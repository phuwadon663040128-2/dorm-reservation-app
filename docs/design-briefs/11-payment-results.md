# 11 — ผลการชำระเงิน / Exception (`/staff/scb/results`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

**จอที่มีเดิมพันสูงสุดในระบบ — การกด "ยืนยันห้องถาวร" ที่นี่คือจุดที่การจองกลายเป็นจริง**

## จอนี้คืออะไร

นำเข้ารายงานผลชำระจาก SCB แล้วทำ 3 อย่างในจอเดียว:

1. **จัดการ exception** — รายการที่ผิดปกติ ต้องมีคนตัดสินใจ
2. **ดูรายการผลนำเข้า** — ตารางผลดิบจากรายงานล่าสุด
3. **ยืนยันห้องถาวร** — กลุ่มที่ชำระครบทุกคนแล้ว กดยืนยันได้

> รายการปกติจับคู่อัตโนมัติ ส่วนผิดปกติเข้าคิวตรวจสอบ — **ไม่ยืนยัน/ปัดตกอัตโนมัติ**

## กฎธุรกิจ

- **RESV-004:** ยืนยันห้องถาวรได้ก็ต่อเมื่อ **ทุกรายการของทุกคนในกลุ่ม** ชำระครบ
- **ยืนยันห้องถาวรเป็น idempotent ทำได้ครั้งเดียว** — ย้อนไม่ได้
- **RESULT-003:** นำเข้ารายงานซ้ำได้ ไม่เกิดรายการซ้ำ
- exception ต้องเลือกวิธีจัดการ + เหตุผลบังคับ + audit
- deadline 72 ชม. เป็นของกลุ่มร่วมกัน ไม่ใช่รายคน

## ปัญหาที่ต้องแก้

1. **สามงานคนละธรรมชาติอยู่ในจอเดียว** — จัดการ exception (ตัดสินใจ), ดูตาราง (อ่าน),
   ยืนยันห้อง (ตัดสินใจแบบย้อนไม่ได้) เจ้าหน้าที่ต้องเลื่อนหาว่างานของตัวเองอยู่ตรงไหน
2. **ปุ่ม "ยืนยันห้องถาวร" กดได้แม้กลุ่มยังไม่ครบ** แล้วค่อยไป toast ปฏิเสธ
   — ปุ่มที่กดไม่ได้ควรบอกตั้งแต่แรกว่าทำไมกดไม่ได้ ไม่ใช่ให้กดแล้วปฏิเสธ
3. **การกระทำที่ย้อนไม่ได้ดูเหมือนปุ่มธรรมดา** — "ยืนยันห้องถาวร" เป็นจุดที่สำคัญที่สุดของทั้งระบบ
   แต่หน้าตาเหมือนปุ่ม submit ทั่วไป ไม่มีขั้นยืนยัน
4. **ตารางผลนำเข้าไม่เชื่อมกับ exception** — เห็น exception แต่ไม่รู้ว่ามาจากแถวไหนของรายงาน
5. **ไม่มีเวลาที่เหลือของกลุ่ม** — กลุ่มที่รอชำระมี deadline 72 ชม. แต่จอนี้ไม่แสดง
   ทั้งที่กลุ่มที่ใกล้หมดเวลาคือกลุ่มที่ต้องตามด่วนที่สุด
6. **ไม่เห็นประวัติการนำเข้า** — แสดงแค่ "รายงานล่าสุด" hard-code batch เดียว
7. exception ไม่มีระดับความรุนแรงหรือการเรียงลำดับ

## โจทย์เฉพาะจอนี้

- **A (Console):** แยกเป็น **แท็บ** — คิวตรวจสอบ · ผลนำเข้า · กลุ่มรอยืนยัน
  โดยแท็บมี badge จำนวนงานค้าง แต่ละแท็บเป็นตารางหนาแน่นพร้อม filter
  · การจัดการ exception และการยืนยันห้องทำผ่าน drawer ที่มีบริบทครบ
- **B (Workflow):** จัดเป็น **สายการผลิต** ตามลำดับที่งานต้องเดิน —
  นำเข้ารายงาน → ผลจับคู่ → เคลียร์ exception → กลุ่มพร้อมยืนยัน → ยืนยันแล้ว
  ทำให้เห็นว่า "ยืนยันห้องไม่ได้เพราะยังมี exception ค้าง" เป็นความสัมพันธ์เชิงเหตุผล ไม่ใช่แค่สอง section
  ปุ่มยืนยันปิดตายพร้อมบอกเหตุผล จนกว่าเงื่อนไขจะครบจริง
- **C (Focus + Split):** ทำเป็น **จอเคลียร์งานทีละเคส** — ซ้ายเป็นคิวรวม (exception + กลุ่มรอยืนยัน ปนกันได้ เรียงตามความด่วน)
  ขวาเป็นเคสที่เลือกพร้อมทุกอย่างที่ต้องใช้ตัดสิน: รายการชำระของกลุ่ม, หน้า PDF ที่เกี่ยว, ประวัติ, ปุ่มจัดการ
  + ปุ่ม "เคสถัดไป"

## เงื่อนไขเพิ่ม

- **ปุ่ม "ยืนยันห้องถาวร" ต้องมี dialog ยืนยันที่:** สรุปว่ากำลังจะยืนยันห้องอะไรให้ใคร
  · เตือนว่า **ทำได้ครั้งเดียว ย้อนไม่ได้** · ต้องกดยืนยันซ้ำ (หรือพิมพ์เลขห้อง) ก่อนผ่าน
- **ปุ่มที่ยังกดไม่ได้ต้อง disabled พร้อมบอกเหตุผลที่เห็นได้ทันที** ไม่ใช่ปล่อยให้กดแล้ว toast ปฏิเสธ
  (แต่ระวัง: ปุ่ม disabled ต้องยังอ่านได้ตามมาตรฐาน contrast และมี tooltip/ข้อความอธิบาย)
- Dialog จัดการ exception ต้องมี: **เลือกวิธีจัดการ** (dropdown) + **เหตุผลบังคับ** + preview ผลที่จะเกิด
- แสดง **deadline / เวลาที่เหลือของแต่ละกลุ่ม** ด้วย `HoldCountdown`
- ต้องมีสภาพ **ไม่มีสิทธิ์** ทั้ง 3 ระดับ: `payment_result.import`, `payment.exception.resolve`, `payment.confirm`
