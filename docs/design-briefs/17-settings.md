# 17 — ตั้งค่าระบบ (`/staff/settings`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

## สถานะปัจจุบัน

**ยังเป็น `PlaceholderPage` — ออกแบบจากศูนย์** (เฟส P5/P6)

## จอนี้คืออะไร

การตั้งค่ากลางของระบบ

> **ค่าที่นโยบายยังไม่นิ่งต้องเป็น configuration ที่แก้ได้ ไม่ hard-code** (เอกสาร 16)

## สิ่งที่ต้องตั้งค่าได้

| หมวด | รายละเอียด |
|---|---|
| สิทธิ์เจ้าหน้าที่ | ผู้ดูแลระบบจัดการที่เมนู "จัดการสิทธิ์เจ้าหน้าที่" แยกต่างหาก — **จอนี้แค่ลิงก์ไป** |
| Dorm scope | กำหนดว่าเจ้าหน้าที่แต่ละคนดูแลหอไหนได้บ้าง |
| Pricing rule | ตั้งค่าราคาแบบ **มีเวอร์ชัน** — แยกจาก override รายรายการ (ที่จอ Obligations) |
| แม่แบบสัญญา | จัดการแม่แบบและเวอร์ชัน |
| ค่า Provisional | ค่าที่รอ stakeholder ยืนยัน (ดูด้านล่าง) |

### ค่า Provisional ที่ยังรอ stakeholder
- นโยบายจ่ายคนเดียว (คนหนึ่งจ่ายแทนทั้งกลุ่มได้ไหม)
- Ref.2 แบบผ่อนชำระ
- ผู้พักที่ยกเว้นค่าธรรมเนียม
- วันต่อสัญญา

## ปัญหาที่ต้องแก้ (โจทย์ตั้งต้น)

1. **ค่าตั้งค่ามีผลกับเงินและสัญญาจริง** — ตั้งผิดคือเสียหายเป็นเงิน
   ต้องมีการยืนยันที่หนักแน่นกว่าฟอร์มตั้งค่าทั่วไป
2. **Pricing rule มีเวอร์ชัน** — ต้องเห็นว่าเวอร์ชันไหนใช้อยู่ เวอร์ชันไหนใช้กับรอบไหน
   และการเปลี่ยนราคาจะไม่กระทบ obligation ที่ออกไปแล้ว
3. **ค่า Provisional ปนกับค่าที่ยืนยันแล้ว** — ต้องแยกให้เห็นชัดว่าอันไหนยังไม่แน่นอนและรออะไรอยู่
4. **ความสัมพันธ์กับจอ Campaigns คลุมเครือ** — Campaigns ตั้งค่ารายรอบ Settings ตั้งค่าระดับระบบ
   ต้องออกแบบให้ผู้ใช้รู้ว่าค่าไหนอยู่ที่ไหน และค่าไหนทับค่าไหน
5. **ไม่รู้ว่าใครแก้ค่าอะไรไปเมื่อไร** — ต้องเชื่อมกับ audit
6. **หมวดตั้งค่า 5 หมวดคนละธรรมชาติ** — สิทธิ์ (ลิงก์ออก), ราคา (มีเวอร์ชัน),
   แม่แบบ (ไฟล์), Provisional (สถานะพิเศษ) จัดรวมกันยังไงไม่ให้สับสน

## โจทย์เฉพาะจอนี้

- **A (Console):** หน้าเดียวแบ่ง section ด้วย sidebar ย่อยซ้าย (anchor nav)
  ทุกค่าแก้ inline ได้ทันที มีแถบ "บันทึกการเปลี่ยนแปลง" ลอยขึ้นเมื่อมีการแก้
  · ค่า Provisional มี badge กำกับทุกตัว · เร็วสำหรับคนที่รู้ว่าจะแก้อะไร
- **B (Workflow):** แยกเป็น **แท็บตามหมวด** แต่ละหมวดมีคำอธิบายว่าค่านี้มีผลกับอะไรบ้าง
  การแก้ค่าสำคัญ (ราคา, แม่แบบสัญญา) ต้องผ่านขั้น: แก้ → preview ผลกระทบ → เหตุผล → ยืนยัน
  มีส่วน "ค่าที่รอ stakeholder" แยกเป็นหมวดของตัวเองพร้อมสถานะว่ารออะไร รอใคร
- **C (Focus + Split):** ซ้ายเป็น tree หมวดตั้งค่า ขวาเป็นฟอร์มของหมวดที่เลือก
  พร้อม **ประวัติการเปลี่ยนแปลงของหมวดนั้น** อยู่ด้านล่างเสมอ (ใคร แก้อะไร เมื่อไร ทำไม)
  ทำให้การตั้งค่ากับ audit เป็นเรื่องเดียวกัน

## เงื่อนไขเพิ่ม

- **ทุกการเปลี่ยนค่าต้องมี dialog ยืนยัน + เหตุผลบังคับ + audit** โดยเฉพาะ pricing rule
- **ค่า Provisional ต้องมี badge ที่ใช้ pattern เดียวกับจอ Campaigns และ Handoff**
  (ออกแบบครั้งเดียวใช้ได้ทั้ง 3 จอ) — ควรบอกได้ว่ารออะไร/รอใคร
- **Pricing rule ต้องแสดงเป็นรายการเวอร์ชัน** ไม่ใช่ค่าเดียวที่แก้ทับ
  พร้อมบอกว่าเวอร์ชันไหนใช้กับรอบไหน และ obligation ที่ออกไปแล้วยึดเวอร์ชันไหน
- ต้องมี **ลิงก์ชัดเจนไปจอ "จัดการสิทธิ์เจ้าหน้าที่"** (`/staff/access`) พร้อมอธิบายว่าทำไมแยกจอ
- ค่าที่ผู้ใช้ปัจจุบันแก้ไม่ได้ (ไม่ใช่ admin) ต้องแสดงเป็น read-only พร้อมเหตุผล ไม่ใช่ซ่อนไปเฉย ๆ
- ตัวเลขเวลาต้องมีหน่วยกำกับเสมอ และแสดงค่าฐานเป็นข้อมูลอ้างอิง

## หมายเหตุ
