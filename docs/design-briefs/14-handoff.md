# 14 — ส่งข้อมูลเข้าระบบมหาวิทยาลัย (`/staff/handoff`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

## จอนี้คืออะไร

ส่งข้อมูลผู้พักที่ยืนยันแล้วเข้าระบบกลางของมหาวิทยาลัย — เป็นปลายทางสุดท้ายของ pipeline ทั้งหมด

> ผู้พักที่ยืนยันแล้วเข้าคิวรอรอบทางการ
> **การแก้ไขภายหลังสร้าง correction export แยก ไม่แก้ทับข้อมูลที่ยื่นไปแล้ว** (HANDOFF-004)

กฎข้อหลังคือแก่นของจอนี้ — ข้อมูลที่ยื่นไปแล้วเป็น **immutable** ทุกการแก้ไขเป็นเอกสารใหม่ที่อ้างถึงของเดิม

## ข้อมูลที่มีจริง

### หัวเพจ
- title: "ส่งข้อมูลเข้าระบบมหาวิทยาลัย"
- description: "ผู้พักที่ยืนยันแล้วเข้าคิวรอรอบทางการ — การแก้ไขภายหลังสร้าง correction export แยก ไม่แก้ทับข้อมูลที่ยื่นไปแล้ว (HANDOFF-004)"
- icon: `SendIcon`
- action: ปุ่ม "สร้างไฟล์ export" ครอบ `PermissionGate permission="university_export.create"`
  toast: "สร้างไฟล์ export ตามคอลัมน์ที่มหาวิทยาลัยกำหนด (**รูปแบบยังรอ stakeholder ยืนยัน**) — เฟส P6"

### การ์ดต่อ 1 batch
หัว:
- `{batch.id}` แบบ `font-mono text-base`
- Badge outline: "ยื่นครั้งแรก" (`kind === 'original'`) หรือ "Correction"
- Badge สถานะ (ชิดขวา)
- คำอธิบาย: "สร้างเมื่อ {วันเวลา} โดย {createdBy}" + ถ้าเป็น correction จะต่อ " · แก้ไขอ้างอิง `{correctsBatchId}`"

เนื้อ: "ผู้พักในชุดนี้: {รายชื่อคั่นด้วย ,}"

### สถานะ batch
| ค่า | label | variant |
|---|---|---|
| `queued` | รอรอบมหาวิทยาลัยเปิด | warning |
| `exported` | ส่งออกไฟล์แล้ว | info |
| `submitted` | ยื่นเข้าระบบมหาวิทยาลัยแล้ว | success |

## กฎธุรกิจ

- **HANDOFF-004:** แก้ไขภายหลัง = สร้าง correction batch ใหม่ที่อ้างถึง batch เดิม ห้ามแก้ทับ
- batch มี 2 ชนิด: `original` และ correction (มี `correctsBatchId`)
- **รูปแบบไฟล์/คอลัมน์ยังไม่ได้ข้อสรุปจาก stakeholder** → ต้องติดป้าย Provisional
- ต้อง minimize ข้อมูลส่วนบุคคลตาม PDPA

## ปัญหาที่ต้องแก้

1. **ความสัมพันธ์ original ↔ correction เป็นแค่ข้อความ** — `correctsBatchId` เป็นตัวหนังสือธรรมดา
   ทั้งที่นี่คือโครงสร้างสำคัญที่สุดของจอนี้ ควรเห็นเป็นสายโซ่ว่า batch ไหนแก้ batch ไหน
   และข้อมูลปัจจุบันที่ถูกต้องคือเวอร์ชันไหน
2. **รายชื่อผู้พักเป็นข้อความยาวคั่นด้วยจุลภาค** — batch จริงมีเป็นร้อยคน อ่านไม่ได้
3. **ไม่เห็นว่าจะส่งอะไรไป** — ไม่มี preview คอลัมน์/เนื้อหาของไฟล์
4. **ไม่มีคิว "รอส่ง"** — จอนี้แสดงแต่ batch ที่สร้างแล้ว
   แต่คำถามแรกของเจ้าหน้าที่คือ "ตอนนี้มีกี่คนรอส่ง" ซึ่งตอบไม่ได้จากจอนี้
5. **สถานะ `queued` = รอรอบมหาวิทยาลัยเปิด** แต่ไม่บอกว่ารอบเปิดเมื่อไร
6. **รูปแบบยัง Provisional** แต่ไม่มี visual บอกเลย — คนใช้อาจเข้าใจว่าเป็นของจริงแล้ว
7. ไม่มีปุ่มดาวน์โหลดไฟล์ที่ export ไปแล้ว

## โจทย์เฉพาะจอนี้

- **A (Console):** ตาราง batch (id · ชนิด · จำนวนคน · สถานะ · วันที่ · ผู้สร้าง · อ้างอิง)
  โดย correction แสดงเป็นแถวย่อยเยื้องใต้ original ของมัน
  · คลิกเปิด drawer ที่มีรายชื่อผู้พักเป็นตารางค้นหาได้ + preview คอลัมน์ไฟล์
  · แถบบนสุดแสดงคิว "รอส่ง N คน" พร้อมปุ่มสร้าง batch
- **B (Workflow):** จัดเป็น **สายส่ง** — รอเข้าคิว → เข้าคิวแล้ว → ส่งออกไฟล์แล้ว → ยื่นแล้ว
  บนสุดคือคิวรอส่งพร้อมจำนวนและปุ่มสร้าง batch
  พร้อมออกแบบ flow **"สร้างไฟล์ export"** เป็นขั้น: เลือกผู้พัก → ตรวจข้อมูลครบ → preview ไฟล์ → ยืนยัน
  มีเส้นทางแยกสำหรับ "สร้าง correction" ที่บังคับให้เลือก batch ต้นทางและระบุว่าแก้อะไร
- **C (Focus + Split):** ซ้ายเป็นรายการ batch จัดเป็น **สายโซ่** (original แล้วตามด้วย correction ทั้งหมดของมัน)
  ขวาเป็นรายละเอียด batch: สรุป + รายชื่อผู้พักแบบตาราง + **diff กับ batch ก่อนหน้า** ถ้าเป็น correction
  (อะไรเปลี่ยนบ้าง) — แก้ปัญหาข้อ 1 ตรงที่สุด

## เงื่อนไขเพิ่ม

- **ต้องมีป้าย "Provisional" ที่ชัดเจน** สำหรับรูปแบบไฟล์ที่ยังรอ stakeholder ยืนยัน
  ออกแบบ pattern ป้ายนี้ให้ใช้ซ้ำได้ในจออื่น (Campaigns และ Settings ก็ต้องใช้)
- **การสร้าง correction ต้องบังคับระบุเหตุผลและอ้าง batch ต้นทาง** — ห้ามสร้างลอย ๆ
- รายชื่อผู้พักในการ์ดต้องยุบได้ (แสดง 5 คนแรก + "และอีก 143 คน" กดกางเต็ม)
- ต้องมีปุ่มดาวน์โหลดไฟล์ซ้ำสำหรับ batch ที่ export แล้ว
- ต้องมีสภาพ **ไม่มีสิทธิ์** (`university_export.create`)
- ไฟล์ export ต้อง minimize ข้อมูลส่วนบุคคล — สะท้อนใน preview ว่าส่งฟิลด์ไหนบ้างเท่านั้น
