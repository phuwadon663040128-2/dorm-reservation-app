# 10 — นำเข้า PDF แบบฟอร์มชำระเงินจากธนาคาร (`/staff/scb/pdf-import`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

**จอที่ซับซ้อนและเสี่ยงผิดพลาดที่สุดจอหนึ่ง — ควรทำในลำดับต้น ๆ**

## จอนี้คืออะไร

ธนาคารส่ง PDF กลับมาเป็น **ไฟล์เดียวรวมหลายหน้า** ระบบต้องแยกหน้าแล้วจับคู่แต่ละหน้า
เข้ากับ obligation ของผู้พักที่ถูกต้อง

> **กฎเหล็ก:** ระบบจับคู่หน้าเข้ากับ obligation จาก **ข้อความเฉพาะของผู้พัก**
> **ห้ามใช้ลำดับหน้า** และ **ห้ามใช้ Ref.1+Ref.2 เพียงอย่างเดียว** (PDF-004/005)

เหตุผลอยู่ในข้อมูลจริง: **รูมเมทใช้ Ref.1/Ref.2 ซ้ำกัน** — จับคู่ด้วย Ref อย่างเดียวจะได้คนผิด
และเอกสารจะไปอยู่กับคนที่ไม่ใช่เจ้าของ

### สถานะการจับคู่
| ค่า | label | variant |
|---|---|---|
| `matched` | จับคู่แล้ว | success |
| `ambiguous` | กำกวม — ต้องตรวจสอบ | warning |
| `unmatched` | จับคู่ไม่ได้ | destructive |
| `superseded` | ถูกแทนที่ | outline |

### หมายเหตุท้ายจอ (อธิบายเคสจริง)
"หน้า 2 กำกวมเพราะ Ref.1+Ref.2 ซ้ำกับหน้าอื่นและไม่มีข้อความระบุตัวผู้พัก —
เคสนี้คือเหตุผลที่ระบบห้าม auto-match จาก Ref อย่างเดียว"

## กฎธุรกิจ

- **manual rematch เฉพาะผู้มีสิทธิ์ + เหตุผลบังคับ + เก็บ mapping เดิมไว้เป็นประวัติ** (PDF-008)
- อัปโหลดต้องเก็บ **ไฟล์ต้นฉบับ + checksum**
- `superseded` แปลว่ามีการจับคู่ใหม่ทับ — ของเดิมยังอยู่ในประวัติ ไม่ถูกลบ

## ปัญหาที่ต้องแก้

1. **เจ้าหน้าที่มองไม่เห็นหน้า PDF จริง** — ให้ตัดสินใจจับคู่จาก "ข้อความที่สกัดได้" ที่ถูก truncate
   ทั้งที่งานนี้ต้องเทียบเอกสารจริงกับผู้พัก **นี่คือปัญหาใหญ่ที่สุดของจอนี้**
2. **หน้าที่ต้องจัดการปนอยู่กับหน้าที่เรียบร้อยแล้ว** — 200 หน้า matched กับ 3 หน้า ambiguous
   อยู่ในตารางเดียวกัน ทั้งที่ 3 หน้านั้นคืองานทั้งหมดของจอนี้
3. **"จับคู่ด้วยมือ" ไม่มี UI จริง** — งานคือเลือก obligation ที่ถูกต้องจากหลายร้อยรายการ
   ต้องมีการค้นหา + แสดงตัวเลือกที่น่าจะใช่พร้อมคะแนนความมั่นใจ
4. **ไม่เห็นภาพรวมของไฟล์** — นำเข้ามากี่หน้า สำเร็จกี่หน้า ค้างกี่หน้า
5. **ไม่มีประวัติการนำเข้า** — เห็นแค่ผลล่าสุด นำเข้าหลายไฟล์แล้วดูย้อนไม่ได้
6. ข้อความที่สกัดได้ถูก truncate จนอ่านไม่ได้ ต้องกางดูได้

## โจทย์เฉพาะจอนี้

- **A (Console):** ตารางหนาแน่นเรียง "ต้องจัดการก่อน" · filter สถานะจับคู่เป็น chip
  · คลิกแถวเปิด drawer **สองฝั่ง**: บนคือ preview หน้า PDF ล่างคือรายการ obligation ที่น่าจะตรง
  พร้อมปุ่มเลือก · มีคีย์ลัดไล่หน้าถัดไป (งานนี้ทำซ้ำ ๆ ความเร็วสำคัญ)
- **B (Workflow):** จัดเป็น **ขั้นตอนการนำเข้า** — อัปโหลด → ระบบแยกหน้า → ผลจับคู่อัตโนมัติ → คิวตรวจสอบ → เสร็จ
  หน้าที่ matched ยุบเป็นสรุปบรรทัดเดียว ("จับคู่อัตโนมัติสำเร็จ 197 หน้า")
  **พื้นที่เกือบทั้งหมดยกให้ 3 หน้าที่ต้องตัดสินใจ** พร้อมบริบทครบสำหรับตัดสิน
- **C (Focus + Split):** **จอตรวจเอกสารเต็มรูปแบบ** — ซ้ายเป็น thumbnail รายการหน้า
  ขวาแบ่งบน/ล่าง: บน = หน้า PDF ขนาดใหญ่, ล่าง = ตัวเลือก obligation + ปุ่มยืนยัน
  มีปุ่ม "หน้าถัดไปที่ต้องตรวจ" — นี่คือแนวทางที่ตรงกับงานจริงที่สุด

## เงื่อนไขเพิ่ม

- **ต้องออกแบบพื้นที่แสดงหน้า PDF** แม้ยังไม่มีไฟล์จริง ให้ใช้กล่อง placeholder
  ที่มีสัดส่วน A4 และมีปุ่มซูม/หมุน/เปิดไฟล์เต็ม
- **UI จับคู่ด้วยมือต้องมี:** ค้นหาผู้พัก · แสดงตัวเลือกที่ระบบเดาว่าน่าจะใช่พร้อมเหตุผล
  · **ช่องเหตุผลบังคับ** · คำเตือนว่า mapping เดิมจะถูกเก็บเป็นประวัติ ไม่ถูกลบ
- ต้องเน้นให้เห็นว่า **หน้าที่กำกวมเกิดจาก Ref ซ้ำ** — แสดงหน้าอื่นที่มี Ref เดียวกันเทียบข้าง ๆ
  เพื่อให้เจ้าหน้าที่ตัดสินได้จริง ไม่ใช่เดา
- แถบสรุปด้านบน: จำนวนหน้าทั้งหมด / matched / ambiguous / unmatched / superseded
- ต้องมีสภาพ **ไม่มีสิทธิ์** ทั้งสองระดับ (`payment_document.import` และ `payment_document.match_review`)
