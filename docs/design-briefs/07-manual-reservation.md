# 07 — จองแทนผู้พัก / Manual Reservation (`/staff/reservations/manual`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

## สถานะปัจจุบัน

**ยังเป็น `PlaceholderPage` — ออกแบบจากศูนย์** (เฟส P5)
ทั้งจอครอบด้วย `<PermissionGate permission="reservation.manual_create">`

## จอนี้คืออะไร

เจ้าหน้าที่ที่มีสิทธิ์สร้างการจองแทนผู้พักได้ทันที — ใช้กับเคสที่นักศึกษาทำเองไม่ได้
(มาที่สำนักงาน, ไม่มีอินเทอร์เน็ต, เคสพิเศษ)

> **การจองแบบนี้เป็น final ทันที ไม่ต้องรอผู้พักยืนยัน**
> นี่คือจอที่มีอำนาจสูงสุดในระบบ — ออกแบบให้ทำได้เร็ว แต่พลาดยาก

## สิ่งที่ต้องทำได้

1. **เลือกห้องจริง** + รูปแบบการพัก (พักคู่ / เหมาห้อง)
2. **ผูกผู้พัก 1–2 คน** — โปรไฟล์ของทุกคนต้องครบก่อน
3. **กรอกเหตุผลบังคับ** + บันทึก audit ทุกครั้ง
4. ใช้ transactional service เดียวกับการจองปกติ — **กันจองซ้อนเหมือนกัน** (HOLD-011)
5. การจองนี้ยังเข้าสู่ workflow ชำระเงิน/สัญญาตามปกติ เว้นแต่มีสิทธิ์ override เพิ่ม

## กฎธุรกิจที่ต้อง validate ใน UI

| กฎ | ต้องบล็อกเมื่อ |
|---|---|
| ห้องต้องว่างจริง | ห้องถูก hold, ถูกจองแล้ว, หรือ block อยู่ |
| โปรไฟล์ครบ | ผู้พักคนใดคนหนึ่ง `profileComplete === false` |
| 1 คน 1 กลุ่ม | ผู้พักอยู่ในกลุ่ม active อื่นอยู่แล้ว |
| จำนวนคนตรงรูปแบบ | พักคู่ต้อง 1–2 คน · เหมาห้องต้อง 1 คน |
| เหตุผล | ช่องเหตุผลว่าง |

**การจองซ้อนอาจเกิดระหว่างที่เจ้าหน้าที่กรอกฟอร์มอยู่** (คนอื่นจองตัดหน้า)
→ ต้องออกแบบว่าจะจัดการยังไงตอนกดยืนยันแล้วห้องไม่ว่างแล้ว

## ปัญหาที่ต้องแก้

1. **เลือกห้องจากรายการหลายร้อยห้องยังไง** — dropdown ยาวเหยียดใช้ไม่ได้
   โปรเจกต์มี **ผังชั้น PNG ใน `public/plans`** และมี room picker แบบผังอยู่ฝั่งนักศึกษาแล้ว
2. **หาคนยังไง** — ต้องค้นด้วยชื่อ/รหัสนักศึกษา/อีเมล และเห็นทันทีว่าคนนี้ผูกได้หรือติดกฎข้อไหน
3. **ทำผิดแล้วแก้ยาก** — เป็นการจอง final ต้องมีขั้นตรวจทานก่อนยืนยัน
4. **บอกให้ชัดว่าต่างจากการจองปกติยังไง** — เจ้าหน้าที่ต้องรู้ว่ากำลังใช้อำนาจพิเศษอยู่

## โจทย์เฉพาะจอนี้

- **A (Console):** ฟอร์มหน้าเดียวหนาแน่น 2 คอลัมน์ — ซ้ายเลือกห้อง (ค้นหา + ผลลัพธ์สด)
  ขวาเลือกคน + เหตุผล มีแถบสรุปด้านล่างตลอดเวลาบอกว่าตอนนี้กรอกครบยัง กดยืนยันได้ไหม
  เหมาะกับเจ้าหน้าที่ที่ทำบ่อยจนจำได้
- **B (Workflow):** **wizard 4 ขั้น** — เลือกห้อง → เลือกรูปแบบ → ผูกผู้พัก → ตรวจทาน+เหตุผล
  แต่ละขั้นตรวจกฎก่อนไปต่อ ขั้นสุดท้ายเป็นใบสรุปเต็มที่ต้องอ่านก่อนกด
  ปลอดภัยที่สุด เหมาะกับคนที่นาน ๆ ทำที
- **C (Focus + Split):** ซ้ายเป็น **ผังห้อง** (grid ตามชั้น) กดเลือกห้องได้เห็นสถานะทุกห้องพร้อมกัน
  ขวาเป็นฟอร์มของห้องที่เลือก — ตอบโจทย์ "หาห้องว่างที่เหมาะ" ซึ่งเป็นงานจริงของเคสหน้าเคาน์เตอร์

## เงื่อนไขเพิ่ม

- **ช่องเหตุผลต้องบังคับกรอกและมีความยาวขั้นต่ำ** ไม่ให้พิมพ์ "." ผ่าน
  แนะนำให้มีตัวเลือกเหตุผลสำเร็จรูป + ช่องอธิบายเพิ่ม
- ต้องมี **สภาพ error ตอนห้องถูกตัดหน้า** — ออกแบบให้ชัดว่าเกิดอะไรและทำอะไรต่อ
- ต้องมี **หน้ายืนยันสำเร็จ** ที่บอกว่าเกิดอะไรขึ้นบ้าง (สร้าง obligation กี่รายการ, deadline เมื่อไร, ขั้นถัดไปคืออะไร)
- ทั้งจอต้องสื่อว่า "นี่คือการกระทำที่มี audit" ตลอดเวลา ไม่ใช่แค่ตอนกดยืนยัน
- ต้องมีสภาพ **ไม่มีสิทธิ์** (`PermissionGate` ไม่ผ่าน)
