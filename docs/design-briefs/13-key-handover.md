# 13 — ส่งมอบกุญแจ (`/staff/key-handover`)

> ต้องอ่าน `00-design-system.md` ก่อน · ออกแบบ 3 แนวทาง A/B/C ตามนิยามในไฟล์นั้น

## จอนี้คืออะไร

บันทึกการส่งมอบกุญแจห้องให้ผู้พัก — เป็น**ขั้นสุดท้ายที่นักศึกษาเข้าอยู่ได้จริง**

> เอกสารลงนามแยกจากสัญญา — ส่งมอบได้เมื่อ **ห้องยืนยันแล้ว + ชำระครบ + สัญญาลงนามครบ + เอกสารประกอบครบ**

จอนี้ต่างจากจออื่นตรงที่ **ใช้งานหน้าเคาน์เตอร์ต่อหน้านักศึกษา** — นักศึกษายืนรออยู่
ความเร็วและการหาเจอทันทีสำคัญกว่าความครบถ้วนของข้อมูล

## ข้อมูลที่มีจริง

### หัวเพจ
- title: "ส่งมอบกุญแจ"
- description: "เอกสารลงนามแยกจากสัญญา — ส่งมอบได้เมื่อห้องยืนยันแล้ว ชำระครบ สัญญาลงนามครบ และเอกสารประกอบครบ"
- icon: `KeyRoundIcon`
- ไม่มีปุ่ม action

ทั้งจอครอบด้วย `<PermissionGate permission="key_handover.record">`

### การ์ดต่อ 1 รายการ (ปัจจุบันเรียงแนวตั้ง)
- กล่องไอคอน `size-10 rounded-lg bg-primary/10 text-primary` + `KeyRoundIcon`
- "ห้อง {roomNumber} — {ชื่อผู้พัก}" ตัวหนา
- Badge สถานะใต้ชื่อ
- ปุ่ม "บันทึกส่งมอบ" — เฉพาะสถานะ `ready` และมีสิทธิ์ `key_handover.record`
  toast: "บันทึกส่งมอบกุญแจพร้อมเอกสารลงนาม (เก็บ private) — เฟส P6"

### สถานะ (`KeyHandoverStatus`)
| ค่า | variant | ความหมาย |
|---|---|---|
| `not_ready` | outline | ยังไม่ครบเงื่อนไข |
| `ready` | warning | พร้อมส่งมอบ รอผู้พักมารับ |
| `signed_handed_over` | success | ส่งมอบแล้ว ลงนามแล้ว |
| `corrected` | info | มีการแก้ไขภายหลัง |
| `cancelled` | outline | ยกเลิก |

(label จาก `keyHandoverStatusLabel`)

## กฎธุรกิจ

**เงื่อนไข 4 ข้อที่ต้องครบก่อนส่งมอบได้:**
1. ห้องยืนยันถาวรแล้ว
2. ชำระเงินครบทุกรายการ
3. สัญญาลงนามครบ (ห้องพักคู่ = ครบทั้ง 2 ฉบับ)
4. เอกสารประกอบครบ

- เอกสารลงนามรับกุญแจเก็บเป็น **private** เสมอ (PDPA)
- สถานะ `corrected` แปลว่ามีการแก้ไขหลังส่งมอบ — ต้องเก็บประวัติเดิม

## ปัญหาที่ต้องแก้

1. **`not_ready` ไม่บอกว่าติดข้อไหน** — นี่คือปัญหาใหญ่ที่สุดของจอนี้
   นักศึกษามารับกุญแจ เจ้าหน้าที่เห็นแค่ "ยังไม่พร้อม" แต่ตอบไม่ได้ว่าติดอะไร
   ต้องเปิดจอสัญญา จอชำระเงิน ไล่ดูทีละจอ **ต่อหน้านักศึกษาที่รออยู่**
2. **ไม่มีค้นหา** — งานหน้าเคาน์เตอร์คือ "นักศึกษาชื่อนี้ ห้องนี้" ต้องหาเจอใน 2 วินาที
   แต่จอนี้ต้องเลื่อนหาเอง
3. **ไม่มี filter** — เห็นทุกสถานะปนกัน ทั้งที่ 99% ของงานคือรายการ `ready`
4. **การ์ดกินพื้นที่แนวตั้งมาก** เห็นได้ไม่กี่รายการต่อจอ
5. **ไม่มีเส้นทางกลับ** — ส่งมอบแล้วอยากดูว่าเมื่อไร ใครเป็นคนบันทึก ทำไม่ได้
6. ไม่มีวันที่/เวลาส่งมอบแสดงในรายการที่ส่งมอบแล้ว

## โจทย์เฉพาะจอนี้

- **A (Console):** ตารางหนาแน่น + **ช่องค้นหาเด่นที่สุดในหน้า** (โฟกัสอัตโนมัติเมื่อเข้าจอ)
  · filter สถานะเป็น chip โดยตั้งต้นที่ "พร้อมส่งมอบ"
  · คอลัมน์ "เงื่อนไข" แสดงเป็นชุดไอคอน 4 ตัว (ยืนยัน/ชำระ/สัญญา/เอกสาร) ติ๊กเขียวหรือกากบาท
  เห็นทันทีว่าติดข้อไหนโดยไม่ต้องเปิดอะไร
- **B (Workflow):** จัดเป็น **checklist ก่อนส่งมอบ** — แต่ละรายการเป็นการ์ดที่กาง 4 เงื่อนไขให้เห็นชัด
  ข้อที่ยังไม่ครบมีลิงก์ไปจอที่แก้ได้ ("สัญญายังไม่ลงนาม → ไปที่จอสัญญา")
  ปุ่มส่งมอบเปิดใช้ได้ก็ต่อเมื่อครบทั้ง 4 — เป็นแนวทางที่ป้องกันการส่งมอบผิดพลาดดีที่สุด
- **C (Focus + Split):** **จอเคาน์เตอร์** — ซ้ายเป็นช่องค้นหา + ผลลัพธ์
  ขวาเป็นหน้ารายละเอียดของผู้พักคนนั้นเต็มหน้า: ตัวตน, ห้อง, เงื่อนไข 4 ข้อ, ปุ่มบันทึกส่งมอบ
  ออกแบบให้อ่านจากระยะห่างได้ (ตัวใหญ่กว่าจออื่น) เพราะใช้ต่อหน้านักศึกษา

## เงื่อนไขเพิ่ม

- **สถานะ `not_ready` ต้องบอกเหตุผลเสมอ** — ห้ามมีคำว่า "ยังไม่พร้อม" ลอย ๆ
  ต้องบอกว่าติดข้อไหนใน 4 ข้อ และลิงก์ไปแก้ได้
- ปุ่ม "บันทึกส่งมอบ" ต้องเปิด dialog ที่มี: ยืนยันตัวตนผู้รับ · อัปโหลดเอกสารลงนาม (private)
  · หมายเลขกุญแจ/จำนวนดอก (ถ้ามี) · ยืนยัน
- รายการที่ส่งมอบแล้วต้องแสดง **วันเวลาและผู้บันทึก**
- ออกแบบให้ทำงานได้ดีบนแท็บเล็ตด้วย (เคาน์เตอร์อาจใช้แท็บเล็ต) — ปุ่มขนาดนิ้วกดได้
- ต้องมีสภาพ **ไม่มีสิทธิ์** (`key_handover.record`)

## Store ที่เรียกใช้

```
useContractsStore() → keyHandovers (id, roomNumber, residentId, status)
                      contracts   (เอาไว้ตรวจเงื่อนไขสัญญา)
usePaymentsStore()  → obligations, isPaid()   (เงื่อนไขชำระเงิน)
useReservationStore() → confirmedReservations  (เงื่อนไขยืนยันห้อง)
usePermissions()    → can('key_handover.record')
fixtures            → users
lib/labels          → keyHandoverStatusLabel
components          → PermissionGate, StaffPageHeader
```
