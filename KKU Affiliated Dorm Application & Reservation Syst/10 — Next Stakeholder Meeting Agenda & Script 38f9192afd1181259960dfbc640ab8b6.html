10 — Next Stakeholder Meeting Agenda & Script

UniPay meeting update

Add UniPay availability, test setup, reference values, final status rule, and fallback evidence flow to the next stakeholder meeting.

See page 12 for full details.

Purpose

Use this page before meeting พี่อ้อม, อาจารย์กานดา, and dorm managers. The goal is to clarify rules and avoid building the wrong system.

Meeting goal

Confirm whether the first live version should be:

  1. Online application only
  1. Online application + UniPay payment or manual evidence upload
  1. Online application + UniPay payment or manual evidence upload + reservation confirmation
  1. Full booking with room availability lock
  1. Integration with existing invoice/payment system

Recommended proposal:

Start with online application + UniPay payment or manual evidence upload + admin verification + reservation status + export.

Suggested opening script

“จากข้อมูลที่ได้รับ พวกผมเข้าใจว่า หอพักในกำกับ เช่น หอพักนพรัตน์ วรเรสซิเดนซ์ และวรอินเตอร์ มีความต้องการที่ต่างจากหอส่วนกลาง เพราะต้องการรับสมัครและจองก่อนรอบปกติของหอส่วนกลาง เพื่อให้ได้ยอดผู้เข้าพักเต็มเร็วขึ้น และบางหอมีเงื่อนไขให้ผู้สมัครชำระเงินหรือค่าประกันตั้งแต่ช่วงสมัคร/จอง ดังนั้นพวกผมอยากเสนอระบบที่ช่วยรับสมัครออนไลน์ อัปโหลดสลิป ตรวจสอบการชำระเงิน ยืนยันการจอง และดูจำนวนห้องว่างได้ครับ”

Key decision questions

Decision 1 — First live dorm scope

Ask:

ถ้าจะเริ่มทำจริง ควรเริ่มจากหอไหนก่อนครับ: หอพักนพรัตน์, วรเรสซิเดนซ์, วรอินเตอร์ หรือทำโครงสร้างให้รองรับทุกหอแต่ pilot แค่หนึ่งหอ?

Recommended answer to propose:

ทำโครงสร้างให้รองรับหลายหอ แต่ pilot หอเดียวก่อน เพื่อไม่ให้ scope ใหญ่เกินไป

Decision 2 — Application or real booking

Ask:

เวอร์ชันแรกต้องการให้เป็น “สมัครออนไลน์ให้แอดมินตรวจ” หรือ “จองห้องจริงพร้อมล็อกจำนวนห้อง” ครับ?

Recommended answer to propose:

เริ่มจากสมัครออนไลน์ + ตรวจสลิป + แอดมินยืนยันการจอง โดยนับจำนวนห้อง/ประเภทห้องก่อน ยังไม่ต้องเลือกห้องจริง

Decision 3 — Exact room or room type

Ask:

ผู้สมัครควรเลือกห้องจริงเลยไหมครับ หรือเลือกแค่ประเภทห้อง/หอ แล้วเจ้าหน้าที่จัดห้องจริงภายหลัง?

Recommended answer to propose:

core product release ให้เลือกประเภทห้องก่อน เพื่อลดความซับซ้อนและลดปัญหาจองชนกัน

Decision 4 — Payment condition

Ask:

แต่ละหออยากให้ผู้สมัครจ่ายอะไรตอนสมัครบ้างครับ เช่น ค่าประกัน, ค่าหอ 1 เทอม, หรือเหมาจ่าย 2 เทอม และต่างกันตามประเภทผู้สมัครไหม?

Follow-up:

  • รุ่นพี่อยู่ต่อจ่ายอะไร?
  • นักศึกษาใหม่จ่ายอะไร?
  • นักศึกษานานาชาติจ่ายอะไร?
  • แต่ละหอมีกฎต่างกันไหม?

Decision 5 — Reservation confirmation source of truth

Ask:

สถานะไหนถือว่า “ได้ห้องแน่นอน” ครับ: สมัครแล้ว, จ่ายแล้ว, อัปโหลดสลิปแล้ว, เจ้าหน้าที่ตรวจสลิปแล้ว, หรือออกใบแจ้งหนี้ในระบบเดิมแล้ว?

Recommended answer to propose:

ในระบบใหม่ให้ถือว่า “จองสำเร็จ” เมื่อเจ้าหน้าที่ตรวจสอบสลิปและกดยืนยันแล้ว ส่วนการออกใบแจ้งหนี้อาจ export ไปทำในระบบเดิมก่อน

Decision 6 — Slip verification owner

Ask:

ใครเป็นคนตรวจสลิปครับ: ผจก.หอ, เจ้าหน้าที่การเงิน, กองบริการหอพัก หรือสองฝ่ายร่วมกัน?

Need to capture:

  • Role name
  • Required fields to check
  • Approval authority
  • Rejection authority

Decision 7 — Existing invoice system

Ask:

ระบบใหม่ต้องเชื่อมกับระบบพิมพ์ใบแจ้งหนี้เดิมตั้งแต่แรกไหมครับ หรือเริ่มจาก export รายชื่อผู้ที่จองสำเร็จ/ตรวจสลิปแล้วไปให้เจ้าหน้าที่ใช้ต่อในระบบเดิมได้ก่อน?

Recommended answer to propose:

เริ่มจาก export ก่อน เพราะ integration ต้องใช้สิทธิ์และข้อมูลจากระบบเดิม

Decision 8 — Current resident renewal

Ask:

รุ่นพี่ที่ประสงค์จะอยู่ต่อ ต้องทำผ่านระบบนี้ตั้งแต่เวอร์ชันแรกไหมครับ หรือช่วงแรกให้หอจัดการ renewal นอกระบบ แล้วใส่จำนวนห้องว่างที่เหลือเข้าระบบ?

Recommended answer to propose:

ช่วงแรกให้แอดมินใส่จำนวนห้องว่างหลัง renewal ก่อน แล้วเฟสถัดไปค่อยทำ renewal online

Decision 9 — Deadline and expiration

Ask:

หลังสมัครแล้วต้องจ่ายภายในกี่ชั่วโมง/กี่วันครับ ถ้าไม่จ่ายหรือไม่อัปโหลดสลิป ห้องควรหลุดอัตโนมัติไหม?

Recommended answer to propose:

ตั้ง deadline ต่อ campaign ได้ เช่น 24 หรือ 48 ชั่วโมง และให้แอดมินเห็นรายการใกล้หมดอายุ/หมดอายุ

Decision 10 — Refund/cancel

Ask:

ถ้าผู้สมัครจ่ายแล้วแต่ยกเลิก มีนโยบายคืนเงินไหมครับ และระบบควรบันทึกสถานะอย่างไร?

Recommended answer:

core product release บันทึกสถานะ cancel/refund request แต่ไม่ automate refund

Data/document request list

Ask stakeholders if they can provide:

  • Current paper application form
  • Dorm list and official names
  • Room type list
  • Price list
  • Deposit/payment rules
  • Example slip/payment instruction
  • Existing Excel/report format
  • Current process diagram if available
  • Required fields for invoice/export
  • Contact person for each dorm

Proposed core product release to show in meeting

Show this simple scope:

Applicant side

  • Open campaign page
  • Fill online form
  • See payment requirement
  • Upload slip
  • Track status

Admin side

  • Create campaign
  • Set room type quota
  • Review applicants
  • Verify slips
  • Approve/reject reservation
  • Export report

Phrases to avoid

Avoid saying:

  • “เราจะมาแทนระบบเดิมทั้งหมด”
  • “เราจะทำระบบชำระเงินจริงทันที”
  • “เราจะใช้ AI ตัดสินว่าใครได้ห้อง”
  • “หอไม่มีระบบออนไลน์เลย”

Better wording:

  • “ระบบนี้ช่วยเสริมขั้นตอนรับสมัครและจองของหอในกำกับ”
  • “ช่วงแรกอาจ export ข้อมูลไปใช้กับระบบเดิมได้”
  • “ระบบออกแบบให้แต่ละหอกำหนดเงื่อนไขเองได้”
  • “เราต้องการลดงานกระดาษและทำให้ตรวจสอบสถานะได้ชัดขึ้น”

Meeting output checklist

After the meeting, fill these in:

  • Confirm applicant types
  • Confirm exact application fields
  • Confirm payment rules
  • Confirm slip verification owner
  • Confirm reservation confirmation rule
  • Confirm room availability model
  • Confirm export format
  • Confirm core product release features
  • Confirm next meeting/demo date

Best closing question

Ask:

ถ้าระบบนี้จะช่วยงานหอได้จริงในเวอร์ชันแรก สิ่งที่จำเป็นที่สุด 3 อย่างที่อยากให้มีคืออะไรครับ?

This forces stakeholders to prioritize and prevents scope explosion.
