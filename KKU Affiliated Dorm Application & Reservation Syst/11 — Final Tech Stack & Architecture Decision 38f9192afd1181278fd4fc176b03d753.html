Decision summary

This page records the current agreed technical stack for the KKU Affiliated Dorm Application & Reservation System.

Final selected stack

Frontend: Nuxt + shadcn-vue + Tailwind CSS
Backend: Go + chi
Database access: GORM + sqlc
Database: PostgreSQL
File/object storage: SeaweedFS
Reverse proxy: Nginx
Runtime/deployment: Docker / Docker Compose
CI/CD: No GitHub Actions for current delivery plan

Why GORM + sqlc together

Use both because they solve different problems.

Use GORM for normal CRUD

GORM should handle most admin/product workflows:

  • Dorm CRUD
  • Room type CRUD
  • Campaign CRUD
  • Applicant CRUD
  • Application CRUD
  • Slip metadata CRUD
  • Admin filters
  • Simple dashboards
  • Settings and role management

Use sqlc for critical correctness

sqlc should handle operations where the SQL must be obvious, reviewable, and transaction-safe:

  • Approve reservation
  • Decrease room type quota
  • Create or expire temporary hold
  • Verify payment and confirm reservation
  • Prevent overbooking
  • Export/report queries
  • Future waitlist promotion

Critical reservation rule

The system must avoid this bug:

remaining quota = 1
Admin A approves applicant
Admin B approves applicant at the same time
Both approvals succeed
System overbooks room type

For this reason, reservation approval should use PostgreSQL transaction logic and atomic SQL, likely through sqlc.

Example logic:

UPDATE campaign_room_type_quotas
SET reserved_count = reserved_count + 1,
    remaining_count = remaining_count - 1
WHERE id = $1
  AND remaining_count > 0
RETURNING id, remaining_count;

If no row is returned, quota is already full and approval must fail safely.

SeaweedFS decision

Use SeaweedFS for uploaded payment slips and documents.

What goes into SeaweedFS

  • Payment slip images
  • Applicant documents
  • Optional dorm photos or attachments
  • Exported files if needed later

What goes into PostgreSQL

PostgreSQL stores metadata only:

  • File ID/key
  • Original filename
  • MIME type
  • Size
  • Uploader ID
  • Related application/payment submission
  • Verification status
  • Created time
  • Access permission metadata

Recommended SeaweedFS setup for core product release

Use SeaweedFS in Docker Compose with services such as:

  • master
  • volume
  • filer
  • optional S3 gateway if the app uses S3-compatible API

Recommended app approach:

  • Prefer S3-compatible API if it makes backend code cleaner.
  • Keep file access private by default.
  • Serve files through backend-authorized endpoints or signed/limited URLs.
  • Do not expose raw payment slips publicly.

Nginx responsibility

Nginx should handle:

  • TLS termination in deployment
  • Reverse proxy to Nuxt frontend
  • Reverse proxy to Go API
  • Upload size limits for slips/documents
  • Optional internal routing to SeaweedFS/filer if needed
  • Security headers

Example route idea:

/             → Nuxt frontend
/api/         → Go chi API
/storage/     → protected file access through backend or internal proxy

Migration decision

Use real migration files, not GORM AutoMigrate as the production source of truth.

Recommended tools:

  • goose, or
  • golang-migrate

GORM AutoMigrate can be useful only for quick local experimentation, but production schema should come from migration files.

Auth and roles

core product release can use simple email/password or mock login, depending on stakeholder needs.

Needed roles:

  • Applicant / Student
  • Dorm Manager
  • Finance Staff
  • Dorm Service Division Admin
  • Super Admin

Future:

  • KKU SSO integration if access is provided.

No GitHub Actions decision

Do not include GitHub Actions in the core product release stack.

Reason:

  • Team can move faster with manual build/deploy or simple scripts.
  • CI/CD can be added later after repository structure, deployment target, and testing strategy are stable.

core product release alternative:

make test
make build
make deploy
# or simple shell scripts used by the team

What is not in core product release stack

Do not add these yet:

  • Kubernetes
  • Kafka
  • Redis unless we discover a clear need
  • Microservices
  • Real payment gateway
  • Full invoice system integration
  • GitHub Actions
  • Complex event bus

Final stack statement for report/presentation

The system uses Nuxt with shadcn-vue for the frontend, Go with chi for the backend API, PostgreSQL as the main database, GORM for normal CRUD, sqlc for critical reservation and reporting queries, SeaweedFS for uploaded slips and documents, Nginx as reverse proxy, and Docker Compose for deployment. GitHub Actions is intentionally excluded from the core product release to keep deployment simple.
