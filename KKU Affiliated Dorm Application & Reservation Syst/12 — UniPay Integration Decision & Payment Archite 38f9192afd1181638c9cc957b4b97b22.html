12 — UniPay Integration Decision & Payment Architecture

Purpose

This page records the payment integration pivot after reviewing the KKU Payment Hub / UniPay API documentation.

Decision summary

The system should no longer assume that manual payment slip upload is the primary payment flow.

New payment architecture:

Primary payment path: UniPay official debt/payment transaction
Fallback path: manual slip upload / manual payment evidence

Why this matters

UniPay appears to provide official KKU payment infrastructure for:

  • Creating debts/payment transactions
  • Querying debts
  • Cancelling unpaid debts
  • Querying transaction logs
  • Generating QR / barcode payment codes
  • Getting receipt token for paid transactions

This means our dorm system should use UniPay as the official payment source of truth if KKU grants API credentials and the dorm unit is allowed to use the relevant project/biller configuration.

UniPay / KKU Payment Hub overview from docs

The documentation describes KKU Payment Hub API as a central payment system for Khon Kaen University.

It supports multiple payment channels such as:

  • QR PromptPay
  • Bill payment barcode
  • Credit card

Relevant API groups seen in the docs:

Authentication

  • POST /oauth/token — request access token
  • GET /oauth/token — introspect current token
  • GET /api/kku/v1/scope — check API scope

Authentication methods:

  • OAuth2 Client Credentials
  • Basic Auth using api_public:api_secret
  • Optional request signing with x-pay-sign-nonce

Debts

  • GET /api/kku/v1/debts — query outstanding debts/transactions
  • POST /api/kku/v1/debts — create debt transaction(s)
  • DELETE /api/kku/v1/debts/{transactionID} — cancel pending debt transaction

Transactions

  • GET /api/kku/v1/transactions — query transaction logs with filters/date ranges

QR & Barcode

  • GET /api/v1/qr/gen30 — generate Tag30 QR code
  • POST /api/v1/qr/gen30 — batch generate Tag30 QR codes
  • GET /api/v1/qr/tag30/{transactionID} — generate Tag30 QR from transaction
  • GET /api/v1/qr/genbillpay — generate bill payment QR/barcode

Receipts

  • GET /api/kku/v1/receipt-token — get receipt token for paid transactions

Payment model change

Old model

Applicant submits form
→ Applicant manually pays outside system
→ Applicant uploads payment slip
→ Staff checks slip manually
→ Reservation confirmed

New preferred model

Applicant submits form
→ Dorm system creates UniPay debt
→ UniPay returns transaction_id
→ Applicant pays using UniPay QR / bill payment / supported channel
→ Dorm system checks UniPay payment status
→ If UniPay status is paid, system marks payment as paid
→ Reservation is confirmed automatically or queued for final dorm admin approval depending on policy

Fallback model

Applicant cannot use UniPay / API access not ready / exceptional case
→ Applicant uploads slip or manual evidence
→ Staff verifies manually
→ Reservation is approved manually

Recommended product decision

Use UniPay as the primary payment integration if credentials and policy approval are available.

Keep manual slip upload as:

  • fallback path
  • exception handling
  • manual evidence upload
  • non-UniPay payment proof
  • temporary core product release mode if credentials are delayed

Updated payment lifecycle

Application Submitted
→ UniPay Debt Created
→ Payment QR/Bill Generated
→ Waiting for Payment
→ UniPay Status Sync
→ Paid by UniPay
→ Reservation Confirmed OR Pending Admin Final Approval

Failure/exception path:

UniPay Debt Created
→ Payment Deadline Passed
→ Debt Cancelled if allowed
→ Application Expired OR Manual Review

Manual fallback path:

Manual Payment Evidence Uploaded
→ Staff Verifying
→ Approved / Rejected / Need Re-upload

Backend service design

Use a provider interface so the system can support UniPay and manual slip fallback.

type PaymentProvider interface {
    CreateDebt(ctx context.Context, req CreateDebtRequest) (*PaymentDebt, error)

}

Updated module responsibilities

UniPay integration module

Responsibilities:

  • Request OAuth token
  • Introspect token
  • Check API scope
  • Create debt/payment transaction
  • Generate QR or bill payment code
  • Query debts
  • Query transaction logs
  • Cancel unpaid debt
  • Get receipt token
  • Sync UniPay status into local database

Manual slip module

Responsibilities:

  • Store payment evidence file in SeaweedFS
  • Store metadata in PostgreSQL
  • Allow staff verification/rejection/re-upload
  • Use only as fallback or exception unless UniPay access is unavailable

What this changes for SeaweedFS

SeaweedFS remains in the stack, but its role changes.

SeaweedFS should store:

  • Application documents
  • Manual payment evidence in fallback cases
  • Exception slips
  • Admin-uploaded evidence
  • Optional exported files

If UniPay is active, most normal payments should not need slip upload as the main proof.

UX changes

Applicant payment screen should show:

  • UniPay payment QR / bill payment code
  • Payment amount
  • Due date
  • Payment status
  • Button to refresh/check payment status
  • Receipt link after paid if available

Manual slip upload should be shown only when:

  • UniPay is unavailable
  • Admin enables manual evidence
  • Applicant is in exceptional/manual review flow

Admin changes

Admin dashboard should show:

  • UniPay Debt Created
  • Waiting for Payment
  • Paid by UniPay
  • Payment Expired
  • Cancelled Bill
  • Manual Review
  • Manual Evidence Uploaded
  • Receipt Available

Admins should no longer need to inspect normal slips when UniPay payment status is available.

Implementation priority

If UniPay access is available soon

core product release should include:

  • Online application
  • UniPay debt creation
  • QR/bill payment display
  • Payment status sync
  • Reservation confirmation
  • Manual fallback only for exceptions

If UniPay access is delayed

core product release should include:

  • Online application
  • Manual slip upload
  • Staff verification
  • Database designed with UniPay fields from day one
  • UniPay integration added when credentials are available

Final payment architecture statement

The system should treat UniPay as the preferred official payment provider and use manual slip upload only as fallback or temporary mode. Reservation confirmation should be tied to UniPay paid status plus any required dorm admin approval, depending on stakeholder policy.
