08 — Payment Rules, Slip Verification & Reservation Lifecycle

UniPay update

Use UniPay as the preferred payment flow when allowed. Manual UniPay payment or manual evidence upload should stay as fallback.

See: 12 — UniPay Integration Decision & Payment Architecture

Purpose

This page defines the most important live-product module: payment conditions, UniPay payment or manual evidence upload, staff verification, and reservation confirmation.

Why this module is central

From stakeholder discussion, affiliated dorms may require applicants to pay during application/reservation. Different dorms and applicant types may have different payment requirements.

Therefore, the system cannot be designed as a normal form only. It needs a configurable payment and verification workflow.

Core concepts

Payment rule

A payment rule defines what an applicant must pay to continue or confirm a reservation.

A payment rule may depend on:

  • Dorm
  • Campaign
  • Room type
  • Applicant type
  • Term/year
  • Student type
  • Manager policy

Payment submission

A payment submission is the applicant’s uploaded evidence.

It includes:

  • Slip file
  • Paid amount
  • Payment date/time
  • Optional reference number
  • Applicant note
  • Verification status

Verification

Verification is the staff action that decides whether the payment evidence is accepted.

Possible results:

  • Verified
  • Rejected
  • Need re-upload
  • Manual review

Reservation

A reservation is the system state that says the applicant has secured a room/room type according to policy.

Recommended rule:

Reservation should become confirmed only after required payment evidence is verified.

Reservation lifecycle

Application created
→ Waiting for payment
→ Slip uploaded
→ Staff verifying
→ Payment verified
→ Reservation approved
→ Reservation confirmed

Alternative failure path:

Slip uploaded
→ Staff verifying
→ Slip rejected
→ Need re-upload
→ Re-uploaded
→ Staff verifying again

Expiration path:

Waiting for payment
→ Deadline passed
→ Application expired
→ Availability returned

Cancellation path:

Reservation confirmed
→ Applicant requests cancellation
→ Admin reviews
→ Cancelled / refund process if applicable

Status definitions

Waiting for Payment

Meaning:

  • Applicant submitted form but has not uploaded required slip.

System behavior:

  • Reservation should not be final.
  • Reminder can be sent.
  • Expire after deadline if no payment evidence.

Slip Uploaded

Meaning:

  • Applicant uploaded evidence.

System behavior:

  • Staff verification queue receives item.
  • Optional temporary hold can start.

Payment Verifying

Meaning:

  • Staff is reviewing payment evidence.

System behavior:

  • Applicant cannot submit another slip unless allowed.
  • Admin can approve/reject/request re-upload.

Need Re-upload

Meaning:

  • Slip was rejected or incomplete.

System behavior:

  • Show rejection reason.
  • Allow re-upload before deadline if policy allows.

Reserved / Approved

Meaning:

  • Staff accepted the application and payment evidence.

System behavior:

  • Availability count decreases.
  • Applicant receives confirmation.
  • Record appears in export/report.

Expired

Meaning:

  • Applicant missed payment or re-upload deadline.

System behavior:

  • Application no longer blocks room.
  • Availability returns.

Verification checklist for staff

When reviewing a slip, staff should check:

  • Correct applicant/application
  • Correct dorm/campaign
  • Correct expected amount
  • Submitted amount matches expected amount
  • Payment date/time is within allowed period
  • Slip is readable
  • Slip is not duplicate if duplicate checking is required
  • Payment channel/account matches expected destination
  • Notes or exceptions if amount differs

Approve action requirements

When staff approves:

  • Status becomes Verified / Reserved.
  • Reviewer ID is stored.
  • Verified time is stored.
  • Reservation record is created or confirmed.
  • Room type quota is updated.
  • Applicant receives notification.
  • Audit log is created.

Reject action requirements

When staff rejects:

  • Rejection reason is required.
  • Applicant receives reason.
  • Staff can choose whether re-upload is allowed.
  • Reservation/hold is released or kept depending on policy.
  • Audit log is created.

Common rejection reasons:

  • Wrong amount
  • Slip unreadable
  • Wrong payment destination
  • Duplicate slip
  • Payment outside allowed date
  • Applicant information mismatch
  • Other / manual note

Temporary hold policy options

Option A — No hold until verification

Pros:

  • Safest against fake/unverified slip.

Cons:

  • Applicant might pay but lose room if verification is slow.

Option B — Hold after application submission

Pros:

  • Applicant feels secure.

Cons:

  • Many applicants can block rooms without paying.

Option C — Hold after UniPay payment or manual evidence upload

Pros:

  • Reduces fake blocking.
  • Gives staff time to verify.

Cons:

  • Still needs timeout and rejection handling.

Recommended core product release:

Hold after UniPay payment or manual evidence upload, confirm after verification.
