05 — Updated Operations: Dorm Manager Workflow & Edge Cases

Official finance flow update

Normal operations should use the university finance status when available. Manual evidence is only a backup process.

Purpose

This page defines the current operations model for the KKU Affiliated Dorm Application & Reservation System.

This page has been cleaned to remove older central-dorm allocation, waitlist-first, and maintenance-heavy assumptions. Those ideas can remain future scope, but the core product release operations are now focused on early recruitment, application campaigns, payment slip verification, reservation confirmation, room type quota, and export/reporting.

Operational model

The real workflow is closer to early recruitment and reservation management than central dorm allocation.

Affiliated dorms want to recruit and secure residents early because they need occupancy to fill quickly and do not want to wait for the normal central dorm booking rounds.

Operational difference from central dorm

Central dorms can define quota proportions such as senior 40% and freshman 60%, with freshman rounds split by admission type.

Affiliated dorms, based on stakeholder discussion, work differently:

Current residents who want to continue stay reserve first
→ remaining rooms are calculated
→ public applications open to other seniors and new students
→ rooms fill as applicants complete required conditions

There is no fixed reserved freshman quota unless the dorm manager creates one.

Current core product release operations

1. Prepare application campaign

Dorm manager/admin sets:

  • Dorm
  • Campaign name
  • Applicant types allowed
  • Room types available
  • Total quota per room type
  • Opening date/time
  • Closing date/time
  • Required payment item
  • Required payment amount
  • Slip upload rule
  • Verification owner/process
  • Cancellation rule
  • Contact channel

2. Optional current resident renewal

If renewal is included in core product release:

  • Current residents confirm whether they want to stay.
  • Admin records or verifies current room/room type.
  • Resident pays required amount if needed.
  • Slip is uploaded and verified if payment is required.
  • Room or room type quota is reserved for resident.
  • Remaining availability is updated.

If renewal is not included in core product release:

  • Dorm handles renewal outside the system first.
  • Admin enters remaining room type quota before public application opens.

3. Public application opens

Public applicants can apply if remaining room type quota exists.

Possible applicants:

  • รุ่นพี่จากหออื่น
  • นักศึกษาใหม่
  • นักศึกษานานาชาติ
  • นักศึกษาทั่วไปตามเงื่อนไขของหอ

4. Verify application and payment slip

Admin/finance checks:

  • Applicant information
  • Applicant type
  • Selected dorm/room type
  • Required payment amount
  • Uploaded slip
  • Payment date/time
  • Duplicate/conflict
  • Available quota

5. Approve or reject reservation

Approval should:

  • Change application status to Approved / Reserved.
  • Mark payment as Verified.
  • Reduce available quota or confirm held quota.
  • Create audit log.
  • Notify applicant or update applicant status page.

Rejection should:

  • Require reason.
  • Notify applicant or update status page.
  • Allow re-upload if policy allows.
  • Release hold if policy requires.
  • Keep audit log.

Reservation policies to decide

Policy 1 — When is room type quota held?

Options:

  1. No hold until slip is verified.
  1. Temporary hold after application submission.
  1. Temporary hold after UniPay payment or manual evidence upload.
  1. Confirm only after admin/staff verification.

Recommended core product release assumption:

Temporary hold after UniPay payment or manual evidence upload, confirmed after staff verification.

Reason:

  • Prevents applicants from blocking rooms without paying.
  • Still gives staff time to verify.

Policy 2 — How long is the hold?

Options:

  • 12 hours
  • 24 hours
  • 48 hours
  • Custom per campaign

Recommended:

Custom per campaign, default 24 hours.

Policy 3 — Who verifies slip?

Options:

  • Dorm manager
  • Finance staff
  • Dorm service division staff
  • Two-step verification

Need stakeholder confirmation.

Policy 4 — What happens after rejected slip?

Options:

  • Applicant can re-upload before deadline.
  • Applicant loses hold immediately.
  • Admin decides manually.

Recommended:

Allow re-upload before deadline, but confirm with stakeholders whether quota hold remains while fixing.

Policy 5 — What happens if applicant pays but quota is full?

Need clear policy before live launch.

Possible handling:

  • Prevent payment/UniPay payment or manual evidence upload if no quota remains.
  • Accept waitlist with refund/manual review.
  • Admin review.

Recommended:

Avoid this case by checking quota before payment/UniPay payment or manual evidence upload unless waitlist payment policy is explicitly defined.

Policy 6 — Refund/cancellation

Needs official policy.

Questions:

  • Can applicant cancel after verified payment?
  • Is payment refundable?
  • Who approves refund?
  • What status should be exported?

For core product release:

Track cancellation/refund status but do not automate refunds.

Operational statuses

Applicant status lifecycle

Not started
→ Application submitted
→ Waiting for payment/slip
→ Slip uploaded
→ Staff verifying
→ Need re-upload OR Approved/Reserved
→ Confirmed OR Cancelled/Expired

Room type quota lifecycle

Total quota
→ available quota
→ temporary hold
→ reserved
→ cancelled/expired returns to available

Edge cases

Edge case 1 — Applicant submits form but never pays

System action:

  • Status remains Waiting for Payment.
  • Reminder can be sent if notification exists.
  • Application expires after deadline.
  • Room/room type is not permanently reserved.

Edge case 2 — Applicant uploads wrong slip

System action:

  • Admin rejects slip with reason.
  • Status becomes Need Re-upload.
  • Applicant can upload again before deadline if allowed.

Edge case 3 — Slip amount does not match required amount

System action:

  • Admin can reject or mark manual review.
  • Reason is required.
  • Applicant is notified or status is updated.

Edge case 4 — Two admins verify same limited room type

System action:

  • Backend must check remaining quota during approval.
  • Approval must use transaction-safe SQL.
  • If quota is already full, approval is blocked and admin sees warning.

Edge case 5 — Current resident renews late

Policy needed:

  • Does current resident lose renewal priority after deadline?
  • Can admin manually keep room?
  • Is there a late fee or manual approval?

Edge case 6 — Public applicant wants exact room

Recommended core product release response:

  • Applicant chooses room type, not exact room.
  • Exact room assignment happens later by admin or future system module.

Edge case 7 — Existing invoice system must be used

core product release response:

  • Export approved/verified list.
  • Staff imports or manually processes in existing system.
  • Direct integration is future scope.

Edge case 8 — Dorm fills before campaign close date

System action:

  • Mark room type full.
  • Optionally close campaign or keep waitlist open.
  • Show full status to applicants.

Edge case 9 — Applicant submits duplicate application

System action:

  • Prevent duplicate active application for same campaign/applicant identity.
  • Admin can merge/cancel duplicate if needed.

Edge case 10 — International applicant has different documents/payment

System action:

  • Applicant type controls required fields/payment rules.
  • International-specific instructions can be shown on campaign page.

Operations principle

The system must help dorm managers fill rooms quickly, but it must also protect against messy records, duplicate applicants, lost slips, unclear reservation status, and overbooking.
