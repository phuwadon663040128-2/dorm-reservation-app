02 — Reservation Rules and Optional Fairness Model

UniPay rule update

If UniPay is available, reservation rules should use UniPay status as the normal signal before final confirmation. Manual evidence remains fallback. See page 12.

Purpose

This page defines the current reservation rules for the KKU Affiliated Dorm Application & Reservation System.

It replaces the older fair-allocation-first model. Allocation, lottery, and priority scoring remain future/optional only.

Current rule model

For affiliated dorms, the main operational need is:

Early application campaign
→ payment requirement
→ UniPay payment or manual evidence upload
→ staff verification
→ reservation confirmation
→ room type quota update

What changed from the old model

The old model treated the project like a central-dorm allocation system.

The current model treats the project as an affiliated dorm reservation operations system.

Current core product release should focus on

  • Current resident renewal-first workflow if stakeholders want it
  • Remaining room/room type availability
  • Public application campaigns
  • Payment rule per dorm/applicant type
  • Slip upload
  • Staff verification
  • Reservation confirmation
  • Export/reporting

Future/optional only

  • Complex fairness allocation engine
  • Priority scoring
  • Lottery/random tie-breaking
  • Advanced waitlist optimization
  • Roommate/group matching

Main reservation rule categories

1. Campaign rule

A campaign is an application/reservation period opened by one dorm or a group of dorms.

Fields:

  • Campaign name
  • Dorm included
  • Room types included
  • Applicant types allowed
  • Open date/time
  • Close date/time
  • Payment deadline
  • Slip upload required or not
  • Staff verification required or not
  • Current resident renewal enabled or not
  • Public application enabled or not
  • Max applicants or room type quota

2. Applicant type rule

Applicant type matters because payment and eligibility may differ.

Possible applicant types:

  • Current resident renewing
  • Senior student from another dorm
  • New first-year student
  • International student
  • Exchange student
  • General applicant

3. Payment rule

Payment rule should be configurable by dorm, campaign, room type, and applicant type.

Examples:

  • Damage deposit only
  • First term payment
  • Full 2-term payment
  • Deposit plus later invoice
  • No payment at application, admin review first
  • Manual payment condition decided by dorm manager

4. Reservation confirmation rule

The system needs to define when a reservation becomes official.

Possible confirmation points:

  • Application submitted
  • Slip uploaded
  • Slip verified by staff
  • Reservation approved by admin
  • Existing invoice/payment system confirmed

Recommended core product release assumption:

Application creates a record. Slip upload may create a temporary hold. Reservation becomes confirmed only after staff verifies the required payment evidence and approves the reservation.

5. Room availability rule

Options:

  • Track exact rooms
  • Track room type quota
  • Track total campaign quota

Recommended core product release:

Track room type quota first. Exact room assignment can happen later.

Current resident renewal-first flow

Current resident renewal phase
→ current resident confirms stay
→ resident pays required amount if needed
→ staff verifies slip if required
→ room or room type is reserved
→ remaining availability is calculated

If renewal is not included in the first build:

Dorm handles renewal outside system
→ admin enters remaining room type quota
→ public application campaign opens

Public application flow

Applicant selects dorm/room type
→ system shows required payment condition
→ applicant submits form
→ applicant uploads slip
→ staff verifies slip
→ system confirms reservation
→ availability count decreases
→ if full, applicant sees closed/waitlist status depending on policy

Temporary hold policy

Option A — no hold until verification

Pros:

  • Safest against fake or invalid payment evidence.

Cons:

  • Applicant may pay but lose quota if verification is slow.

Option B — hold after application submission

Pros:

  • Applicant feels secure early.

Cons:

  • Applicants can block rooms without paying.

Option C — hold after UniPay payment or manual evidence upload

Pros:

  • Reduces fake blocking.
  • Gives staff time to verify.

Cons:

  • Still needs timeout and rejection handling.

Recommended core product release assumption:

Hold after UniPay payment or manual evidence upload, confirm after staff verification.

Waitlist rule

Waitlist is optional for core product release.

Options:

  1. Close room type when quota is full.
  1. Allow waitlist without payment.
  1. Allow waitlist with manual review only.
  1. Allow paid waitlist only if official refund policy is clear.

Recommended core product release:

Start by closing full room types or allowing non-paid waitlist only. Do not accept payment for waitlist unless refund/priority policy is officially confirmed.

Critical business questions

These must be confirmed with พี่อ้อม / dorm managers / อาจารย์กานดา:

  1. Does applicant choose exact room or only room type?
  1. Is quota held after application, after UniPay payment or manual evidence upload, or after staff verification?
  1. How long is the temporary hold?
  1. Who verifies payment slip?
  1. Can staff reject slip and allow re-upload?
  1. What happens if applicant pays but quota is already full?
  1. What happens if applicant cancels after payment?
  1. Does the system create official invoice data or export to existing system?
  1. Which status counts as official “ได้ห้องแล้ว”?
  1. Should current resident renewal be included in core product release?

Final rule direction for core product release

The core product release should not try to solve central-dorm fairness allocation. It should provide a clean operational workflow for affiliated dorms: campaign setup, room type quota, applicant form, payment rule display, UniPay payment or manual evidence upload, staff verification, reservation confirmation, export/reporting, and audit log.
