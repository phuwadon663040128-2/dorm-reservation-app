04 — Updated Technical Architecture: Campaigns, Reservations & Slip Verification

UniPay architecture update

Add a UniPay connector module as the preferred official path when approved. Keep manual evidence upload as fallback. See page 12 for full design.

Purpose

This is the current technical architecture page for the KKU Affiliated Dorm Application & Reservation System.

This page supersedes the older allocation-engine / React-Next / Node.js prototype notes. The current implementation direction is Go + chi, Nuxt, PostgreSQL, GORM + sqlc, SeaweedFS, Nginx, and Docker Compose.

Final implementation stack

Frontend: Nuxt + shadcn-vue + Tailwind CSS
Backend: Go + chi
Database access: GORM + sqlc
Database: PostgreSQL
File/object storage: SeaweedFS
Reverse proxy: Nginx
Runtime/deployment: Docker / Docker Compose
CI/CD: No GitHub Actions for core product release

Full detail: 11 — Final Tech Stack & Architecture Decision

Architecture goal

The architecture should support campaign-based online applications, payment rule configuration, UniPay payment or manual evidence upload and verification, reservation status tracking, room type quota management, and export/reporting for affiliated dorm operations.

The core product release should not overbuild central-dorm-style allocation logic. Allocation/fairness modules can remain future extensions.

Backend module boundaries

1. Auth and role module

Responsibilities:

  • Login/session handling
  • Role detection
  • Permission middleware
  • Future KKU SSO integration point

Roles:

  • Applicant / Student
  • Dorm Manager
  • Finance Staff
  • Dorm Service Division Admin
  • Super Admin

2. Campaign module

Responsibilities:

  • Create/edit/open/close application campaigns
  • Define dorm and room types included
  • Define applicant types allowed
  • Define campaign dates and deadlines

Key tables:

  • campaigns
  • campaign_room_type_quotas

3. Dorm and room type module

Responsibilities:

  • Manage dorms
  • Manage room types
  • Manage price/deposit/facility information
  • Manage quota or availability by room type

core product release decision:

  • Track room type quota first.
  • Exact room selection is future scope.

4. Application module

Responsibilities:

  • Store applicant form data
  • Store selected campaign and room type
  • Track application status
  • Prevent duplicate active applications per campaign/applicant identity

5. Payment rule module

Responsibilities:

  • Define required payment per dorm/campaign/room type/applicant type
  • Define amount, payment item, deadline, and verification requirement

Payment items:

  • Damage deposit
  • Reservation fee
  • Room fee 1 term
  • Room fee 2 terms
  • Other dorm-specific fee

6. Slip upload and verification module

Responsibilities:

  • Upload payment slip file to SeaweedFS
  • Store file metadata in PostgreSQL
  • Store expected amount and submitted amount
  • Let staff verify, reject, or request re-upload
  • Keep verification history and audit log

7. Reservation module

Responsibilities:

  • Create temporary hold if policy uses hold
  • Confirm reservation after verification
  • Prevent overbooking
  • Expire unpaid/unverified applications if needed
  • Cancel reservation with reason

8. Export and reporting module

Responsibilities:

  • Export approved reservations
  • Export verified payment records
  • Export applicants waiting for payment/slip
  • Export campaign summary
  • Support existing invoice/payment workflow without direct integration in core product release

9. Audit log module

Responsibilities:

  • Log sensitive staff actions
  • Record old/new values and reasons
  • Support review of approve/reject/cancel/expire actions

GORM + sqlc split

Use both GORM and sqlc intentionally.

GORM is for normal CRUD

Use GORM for:

  • Dorm CRUD
  • Room type CRUD
  • Campaign CRUD
  • Applicant CRUD
  • Application CRUD
  • Slip metadata CRUD
  • Admin filters
  • Simple dashboard queries
  • Settings and role management

sqlc is for critical SQL

Use sqlc for operations where exact SQL must be obvious and transaction-safe:

  • Approve reservation
  • Decrease room type quota
  • Create/expire temporary hold
  • Verify payment and confirm reservation
  • Prevent overbooking
  • Export/report queries
  • Future waitlist promotion

Critical quota rule

The system must avoid overbooking.

Danger scenario:

remaining quota = 1
Admin A approves applicant
Admin B approves applicant at almost the same time
Both approvals succeed
System overbooks room type

Use PostgreSQL transaction-safe SQL for approval.

Example:

UPDATE campaign_room_type_quotas
SET reserved_count = reserved_count + 1,
    remaining_count = remaining_count - 1
WHERE id = $1
  AND remaining_count > 0
RETURNING id, remaining_count;

If no row is returned, quota is already full and approval must fail safely.

SeaweedFS file storage design

SeaweedFS stores the actual files:

  • Payment slip images
  • Applicant documents
  • Optional dorm attachments
  • Optional exported files

PostgreSQL stores metadata only:

  • File key/path
  • Original filename
  • MIME type
  • File size
  • Uploaded by
  • Related application/payment submission
  • Verification/access status
  • Created time

Recommended SeaweedFS services in Docker Compose:

seaweed-master
seaweed-volume
seaweed-filer

Optional later:

seaweed-s3

Use the S3 gateway only if the backend implementation becomes cleaner with an S3-compatible client.

Nginx responsibility

Nginx should handle:

  • Reverse proxy to Nuxt frontend
  • Reverse proxy to Go API
  • TLS termination in deployment
  • Upload size limits for slips/documents
  • Optional protected file proxy route
  • Security headers

Route idea:

/             → Nuxt frontend
/api/         → Go chi API
/storage/     → protected file access through backend or internal proxy

core product release implementation notes

Phase 1 live core product release:

  • No real payment gateway
  • No exact room selection
  • No real KKU SSO unless access is provided
  • Use room-type quota
  • Use UniPay payment or manual evidence upload and manual verification
  • Use SeaweedFS for uploaded slips/documents
  • Use CSV export for existing invoice/payment workflow
  • Use manual scripts instead of GitHub Actions

Phase 2:

  • Current resident renewal module
  • Temporary hold timeout
  • Waitlist when room type is full
  • More detailed reporting
  • Role-based staff accounts

Phase 3:

  • Integration with existing invoice system
  • KKU SSO integration
  • Automatic slip verification if payment channel supports it
  • Exact room assignment
  • Check-in and maintenance modules

Technical risks

Risk 1 — payment evidence mismatch

Mitigation:

  • Store expected amount and submitted amount.
  • Require staff verification.
  • Allow reject/re-upload flow.
  • Keep audit log.

Risk 2 — overbooking

Mitigation:

  • Use database constraints and transaction-safe SQL.
  • Use sqlc for critical reservation/quota updates.
  • Block approval when no quota remains.

Risk 3 — unclear source of truth

Mitigation:

  • Confirm whether this system or the existing invoice system is the official confirmation.
  • In core product release, treat this system as application/reservation management and export to official process.

Risk 4 — private slip/file handling

Mitigation:

  • Store files in SeaweedFS, not app container.
  • Restrict file access to authorized roles.
  • Serve slips through protected backend endpoints.
  • Do not expose raw payment slips publicly.
