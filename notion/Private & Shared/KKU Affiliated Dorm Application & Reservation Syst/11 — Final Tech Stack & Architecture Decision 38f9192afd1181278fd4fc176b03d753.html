11 — Final Tech Stack & Architecture Decision

Decision summary

Last revised: 2026-07-10

This page records the selected implementation stack and architectural constraints for the combined exact-room pilot of หอ 8 หลัง + วรอินเตอร์.

Final selected stack

Frontend: Nuxt + shadcn-vue + Tailwind CSS
Backend: Go + chi
Database access: GORM + sqlc
Database: PostgreSQL
File/object storage: SeaweedFS via S3-compatible gateway
Reverse proxy: Nginx
Runtime/deployment: Docker / Docker Compose
Applicant authentication: verified internal email/password account
Optional identity: Mock/production KKU SSO adapter
External payment workflow: SCB XLSX export, returned multipage PDF, payment-result import
CI/CD: no GitHub Actions in current delivery plan

Core architecture decisions

Exact rooms, not only room-type quota

The MVP stores and reserves exact rooms. Room numbers are globally unique and map to building/floor context.

Roommate group is a first-class domain

The system stores:

  • reservation leader;
  • invitation/acceptance;
  • one active group per resident;
  • maximum two residents;
  • optional second room confirmation;
  • group payment deadline;
  • grouped contract completion.

Whole-room rental is a first-class occupancy mode

It is not implemented as a fake second roommate. One resident blocks both occupancy slots and receives full-room obligations.

SCB workflow is file exchange

Our app does not generate official QR bills and does not use a direct bank API in the MVP.

It generates the required Excel batch, imports the returned combined PDF, and imports the result report.

Paper contracts remain official operational output

Our app generates printable contracts, stores immutable snapshots, records physical signatures and private scans, and tracks separate key handover.

Used where correctness must be reviewable:

Document-processing decisions

XLSX

Use a library that preserves:

  • exact worksheet name;
  • column order;
  • numeric amount types;
  • date values/format accepted by the internal application;
  • blank ID cells;
  • field length validation.

Returned PDF

  • Store original combined PDF.
  • Extract text layer page by page.
  • Match by resident-specific text and obligation context.
  • Do not use OCR unless PDF is image-only.
  • Never depend only on page order or Ref.1 + Ref.2.
  • Preserve manual mapping decisions and reasons.

Contract rendering

Use a versioned template and immutable generated snapshot. A rendered PDF is a printable artifact, not an electronic signature.

Critical database constraints

  • Unique room number.
  • Maximum two active reservation members.
  • One active roommate group/invitation per resident.
  • Whole-room assignment prevents second occupant.
  • One active hold per room.
  • One active room per reservation group.
  • Every obligation references one resident, room, group, action, cycle, and price source.
  • Ref.1 + Ref.2 is not unique.
  • Re-imported SCB batch/result is idempotent.
  • Superseded obligations/contracts remain immutable history.

Critical concurrency rule

The system must avoid:

Room A101 is available
Leader A reserves it
Leader B reserves it at the same time
Both receive a successful hold

Use a single transaction/conditional update or row lock. Only one hold succeeds.

The same rule applies to:

  • hold expiry/release;
  • permanent confirmation;
  • roommate replacement;
  • result-report application;
  • correction export.

Audit decisions

Always log actor, scope, reason, before/after, related IDs, timestamp, and request/idempotency key for:

  • manual reservation/payment;
  • amount override/pricing update;
  • room block/release override;
  • cancellation;
  • roommate replacement;
  • PDF page rematch/replacement;
  • payment exception decision;
  • final confirmation;
  • contract reprint/correction/cancellation;
  • key handover correction;
  • university correction export.

Migration decision

Use versioned migration files as source of truth. GORM AutoMigrate is not the production migration process.

Recommended tools:

  • goose; or
  • golang-migrate.

Testing baseline

  • room hold concurrency;
  • invitation/group constraints;
  • 15-minute and 72-hour expiry;
  • one paid/one unpaid group;
  • shared-to-whole conversion;
  • XLSX contract validation;
  • reordered PDF with duplicate room/action references;
  • ambiguous page mapping;
  • repeated result import;
  • manual payment permission;
  • obligation/contract supersession;
  • university correction history;
  • private file authorization;
  • backup/restore across database and files.

No GitHub Actions decision

Manual/local scripts remain acceptable for current delivery:

make test
make build
make fixtures
make deploy

CI may be added later after repository and deployment target stabilize.

Deferred technical scope

  • real-time bank API/webhook;
  • digital signature infrastructure;
  • monthly utility implementation;
  • parcel/maintenance modules;
  • Kubernetes/microservices/event bus;
  • Redis unless a proven need appears.

Final stack statement

The system uses Nuxt with shadcn-vue for the applicant and staff interfaces, Go with chi for the API and domain services, PostgreSQL for exact-room and payment integrity, GORM for normal CRUD, sqlc for concurrency-critical operations, SeaweedFS through an S3-compatible gateway for private documents, Nginx as the public reverse proxy, and Docker Compose for reproducible deployment. Official QR forms and payment results are exchanged with the existing SCB workflow through XLSX, multipage PDF, and result-report files.
