04 — Technical Architecture: Exact Rooms, Roommates & SCB File Exchange

Purpose

Last revised: 2026-07-10

This page defines the implementation architecture for the accepted pilot covering หอ 8 หลัง and วรอินเตอร์ together.

Core architecture changes:

  • exact-room inventory is mandatory;
  • roommate groups and whole-room rental are core;
  • our app exports SCB Bill Payment Excel batches;
  • the existing SCB/internal software returns combined multipage QR PDFs and payment-result reports;
  • applicant slip upload and one shared static QR are no longer the normal payment path;
  • contracts are generated for physical signing;
  • university-system submission is a queued export/correction workflow.

Final implementation stack

Frontend: Nuxt + shadcn-vue + Tailwind CSS
Backend: Go + chi
Database access: GORM + sqlc
Database: PostgreSQL
File/object storage: SeaweedFS via S3-compatible gateway
Reverse proxy: Nginx
Runtime/deployment: Docker / Docker Compose
Identity: verified internal applicant accounts; optional KKU SSO
External file exchange: SCB XLSX import, returned multipage PDF, SCB payment-result report
CI/CD: no GitHub Actions in the current delivery plan

Architecture boundary

Our app is authoritative for

  • internal users and applicant profiles;
  • dorm/building/floor/exact-room inventory;
  • room configuration versions and occupancy modes;
  • roommate invitations and groups;
  • room holds and exact-room assignments;
  • pricing rules, overrides, and resident obligations;
  • SCB export batches and rows;
  • returned PDF files and page mappings;
  • imported/manual payment states;
  • reservation confirmation;
  • printed contracts, scans, and key handover;
  • queued university handoff and correction history;
  • audit logs.

SCB/internal software is authoritative for

  • accepting the required SLIPS workbook;
  • generating official QR Bill Payment forms;
  • returning payment-result data.

University systems remain authoritative for

  • official university accounting and receipt records;
  • Payment Hub/ERP records after handoff.

Backend module boundaries

1. Authentication and role module

Responsibilities:

  • verified personal-email registration;
  • password/session/recovery;
  • optional KKU SSO login/linking;
  • role, dorm, campaign, and action-scoped permissions.

KKU SSO does not gate reservation, payment, contract, or key handover.

2. Exact-room inventory module

Responsibilities:

  • dorm/building/floor/room CRUD;
  • globally unique room number;
  • room dimensions, plan reference, facilities, and equipment;
  • current room configuration and historical versions;
  • occupancy capacity and shared/whole-room capability;
  • public availability projection.

Recommended tables:

  • dorm_groups
  • buildings
  • floors
  • rooms
  • room_config_versions
  • room_assets
  • room_occupancy_slots

3. Roommate and reservation-group module

Responsibilities:

  • one active invitation/group per resident;
  • maximum group size two;
  • invitation expiration after 48 hours;
  • reservation leader;
  • configurable second room confirmation;
  • 15-minute confirmation hold;
  • staff manual reservation;
  • renewal and replacement history.

Recommended tables:

  • roommate_groups
  • roommate_invitations
  • reservation_groups
  • reservation_members
  • reservation_group_events

4. Exact-room hold and assignment module

Responsibilities:

  • atomic room hold on leader reservation;
  • 15-minute roommate-confirmation hold;
  • 72-hour group payment hold;
  • release/expiry exactly once;
  • permanent exact-room confirmation;
  • shared versus whole-room occupancy;
  • concurrency-safe reservation.

Recommended tables:

  • room_holds
  • room_assignments
  • room_status_events

Critical rule:

UPDATE rooms
SET active_hold_id = $hold_id,
    status = 'held'
WHERE id = $room_id
  AND status = 'available'
  AND active_hold_id IS NULL
RETURNING id;

No returned row means another reservation already holds the room.

5. Pricing and obligation module

Responsibilities:

  • pricing by exact room/configuration, occupancy mode, applicant type, year/cycle, and payment action;
  • separate ROOM and HL obligations;
  • one resident × one action obligations;
  • full-room amounts;
  • finance-only one-off override with reason;
  • separate permanent pricing-rule update.

Recommended tables:

  • payment_actions
  • pricing_rules
  • pricing_rule_versions
  • payment_obligations
  • payment_obligation_events

6. SCB export module

Responsibilities:

  • select ready obligations;
  • validate field lengths and required values;
  • generate .xlsx with worksheet SLIPS;
  • leave ID blank;
  • write Payer Name, Ref.1, Ref.2, numeric amount, bill issue date, email, DEFAULT, and remark;
  • preserve batch/row/checksum history;
  • support configurable batch grouping.

Recommended tables:

  • payment_export_batches
  • payment_export_rows
  • payment_export_files

7. Returned PDF module

Responsibilities:

  • private storage of original combined PDF;
  • page count, checksum, and import actor;
  • text extraction from each page;
  • match page to resident obligation using resident-specific text and context;
  • reject ambiguous Ref.1 + Ref.2-only matching;
  • manual rematch with reason;
  • preserve superseded versions.

Recommended tables:

  • returned_payment_documents
  • returned_payment_document_pages
  • payment_document_matches

Use text-layer extraction first. OCR is a fallback only if the returned PDF is image-only.

8. Payment-result and exception module

Responsibilities:

  • import SCB downloadable result report;
  • normalize transaction/reference fields;
  • match to obligations;
  • mark paid/unpaid;
  • send underpayment, overpayment, duplicate, late, and post-expiry payment to review;
  • support manual payment with bank reference and staff note;
  • confirm group payment completion.

Recommended tables:

  • payment_result_imports
  • payment_result_rows
  • payment_transactions
  • payment_exception_cases
  • refund_status_events

9. Contract and key-handover module

Responsibilities:

  • versioned contract template;
  • immutable populated snapshot;
  • two resident contracts under a shared group;
  • one whole-room contract;
  • applicant/staff printing;
  • reprint/correction history;
  • private signed scan/photo;
  • group completion when both shared-room contracts are received;
  • separate signed key-handover record.

Recommended tables:

  • contract_templates
  • contract_template_versions
  • contracts
  • contract_print_events
  • contract_status_events
  • signed_contract_files
  • key_handover_records

10. Renewal module

Responsibilities:

  • configurable renewal campaign;
  • prefill and reconfirm prior data;
  • preserve current room when allowed;
  • replacement invitation / whole-room / move / release choices;
  • leader change with both residents’ confirmation;
  • supersede old obligations/contracts without destructive overwrite.

11. University handoff module

Responsibilities:

  • queue confirmed residents until the university round opens;
  • export approved rows;
  • store original submission batch;
  • create correction batch for later roommate/room/amount changes;
  • preserve original and correction records.

12. Audit module

Log:

  • manual reservation/payment;
  • exact-room override/block;
  • amount override/pricing update;
  • PDF rematch/replacement;
  • payment exception decision;
  • confirmation/release/cancellation;
  • roommate replacement;
  • contract reprint/correction;
  • key handover;
  • university correction export.

GORM and sqlc split

Use GORM for normal CRUD and staff screens.

Use sqlc/explicit SQL for:

  • exact-room hold acquisition/release;
  • hold expiry;
  • group confirmation;
  • obligation generation and supersession;
  • payment-result idempotency;
  • final reservation confirmation;
  • correction export queries;
  • audit-sensitive reporting.

File storage

Private SeaweedFS buckets/areas:

  • applicant-documents
  • scb-export-files
  • scb-returned-pdfs
  • scb-payment-results
  • contracts
  • signed-contracts
  • key-handover
  • university-exports

All file access goes through backend authorization. Raw S3/SeaweedFS endpoints are never public.

Idempotency and concurrency requirements

  • Room hold requests use idempotency keys.
  • Expiry/release can run repeatedly without double release.
  • Returned PDF re-upload does not duplicate page records.
  • Payment-result report re-import does not double-apply transactions.
  • Final confirmation succeeds at most once.
  • Replacement supersedes old obligations/contracts exactly once.
  • University correction does not erase the original submission.
