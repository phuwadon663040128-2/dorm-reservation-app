This page converts the accepted eight-month roadmap into an implementation sequence for the combined วรเรสซิเดนซ์ / หอ 8 หลัง + หอพักวรอินเตอร์ pilot.

It does not change the approved scope. It breaks the current direction into repository work, database migrations, APIs, frontend screens, file-processing jobs, tests, acceptance gates, deployment work, and stakeholder checkpoints.

Delivery assumptions

  • Two-week implementation sprints, Monday–Friday.
  • Planned execution window: 2026-07-13 through 2027-02-28.
  • If the official start moves, preserve the dependency order and exit criteria rather than the exact dates.
  • A small team may combine roles; ownership below describes responsibility, not required headcount.
  • The team uses manual/local build and release scripts. GitHub Actions remains outside the current plan.
  • External SCB and university systems remain file-exchange boundaries. They are not services owned or deployed by this project.
  • Unknown operational rules remain configurable and marked Provisional; they must not be hard-coded as official policy.

Non-negotiable implementation rules

  1. Exact room is the reservation inventory source of truth.
  1. A room number is globally unique.
  1. A room can have only one active hold.
  1. A resident can have only one active roommate invitation/group.
  1. Maximum normal group size is two residents.
  1. Whole-room rental is a real occupancy mode, not a fake second resident.
  1. Leader reserve action atomically holds the exact room.
  1. Required roommate room confirmation expires after 15 minutes.
  1. Successful group confirmation creates a 72-hour payment hold.
  1. Shared residents receive separate obligations and share one room-group deadline.
  1. HL creates separate ROOM and HL obligations.
  1. Ref.1 + Ref.2 is not a unique resident/payment key.
  1. Official QR forms come from the existing SCB/internal application.
  1. Returned PDF matching must not depend on page order.
  1. Final room confirmation is transaction-safe and succeeds at most once.
  1. Superseded payments, contracts, exports, and corrections remain immutable history.
  1. Manual reservation/payment, amount override, cancellation, replacement, rematch, reprint, and correction require a reason and audit event.
  1. All uploaded and generated files are private and served only through backend authorization.

Definition of done for every implementation item

A feature is complete only when:

  • database migration is versioned and reversible where practical;
  • domain rule and authorization are enforced server-side;
  • API request/response contract is documented;
  • frontend handles loading, empty, success, permission-denied, validation, conflict, and retry states;
  • audit behavior is implemented when applicable;
  • unit and integration tests pass;
  • concurrency/idempotency tests exist for state-changing critical actions;
  • private-file access is tested;
  • fixture or demo data exists;
  • acceptance criteria are demonstrated in a reproducible environment;
  • operational documentation is updated.

Sprint 9 — Returned multipage PDF import and page matching

Dates: 2026-11-16 to 2026-11-27

Goal: Attach the correct official QR form to each resident obligation.

Backend/document processing

  • Store original combined PDF and checksum.

  • Match by resident-specific text plus obligation context.
  • Explicitly reject room/action-only uniqueness.
  • Confidence/result states: matched, ambiguous, unmatched, superseded.
  • Manual rematch with reason.
  • Replacement/supersession history.
  • Image-only fallback path isolated behind an interface.

Frontend

  • Combined PDF upload.
  • Page thumbnail/text/match review.
  • Ambiguous/unmatched queue.
  • Manual mapping and reason.
  • Applicant payment-form viewer/download.

Tests

  • Reordered pages.
  • Two roommates with identical Ref.1 and Ref.2.
  • Duplicate resident text.
  • Missing page and extra page.
  • Re-upload same PDF.
  • Replacement PDF preserves previous mapping history.

Exit criteria

  • Every matched resident sees only their own official payment form.
  • Page order is never used as identity.

Security and PDPA implementation checklist

  • Strong password hashing and expiring verification/reset tokens.
  • Secure, HTTP-only, same-site cookies when using cookie sessions.
  • CSRF protection for state-changing browser requests.
  • Rate limits for authentication, invitations, reservation attempts, and file imports.
  • Role + dorm + action authorization on every staff endpoint.
  • Private buckets and backend-authorized downloads.
  • MIME, extension, size, and checksum validation.
  • No production tokens or secrets in database logs.
  • Data minimization in exports and dashboards.
  • Audit access to sensitive files and corrections.
  • Retention configuration for application files, SCB artifacts, contracts, and audit logs.
  • Breach-response and access-review runbooks before pilot.
  • Test accounts and fixtures contain no real personal or bank data.
