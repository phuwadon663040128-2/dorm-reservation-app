Purpose and status

Status: Canonical test-first execution plan for AI-assisted implementation

Implementation plan: 16 — Detailed Implementation Plan & Sprint Execution

Fixture source: 15 — Mock SSO, Exact-Room, SCB Export/PDF & Payment Fixtures

This page turns the approved implementation plan into a deterministic test base that a coding AI can follow one vertical slice at a time. It does not change product scope or unresolved policy. Every implementation change must begin from named test cases, fixed fixtures, explicit API/data contracts, and a limited file-change boundary.

Primary objective

Make implementation safe for an AI coding agent by ensuring that each task has:

  • one unambiguous behavior;
  • stable fixture inputs;
  • a failing test before production code changes;
  • exact commands to run;
  • expected outputs and error codes;
  • explicit permitted files/migrations;
  • no hidden policy assumptions;
  • traceability to requirement, sprint, and test ID;
  • a human-reviewable diff and completion report.

flowchart LR

    B --> C[Write failing unit or integration test]
    C --> D[Implement minimum production code]
    D --> E[Run targeted test]
    E -->|Fail| D
    E -->|Pass| F[Run module suite]
    F -->|Fail| D
    F -->|Pass| G[Run API, document, and database contract tests]
    G -->|Fail| D
    G -->|Pass| H[Run end-to-end and concurrency tests]
    H -->|Fail| D
    H -->|Pass| I[Update manifest, docs, and traceability]
    I --> J[Human review and merge]

    K[Provisional policy flag] --> A
    L[No real personal or bank data] --> B
    M[Deterministic clock and IDs] --> C
    N[Immutable history and audit] --> D

Non-negotiable AI coding rules

  1. Do not invent or change dorm policy. Unknown policy remains behind configuration or a clearly named provisional feature flag.
  1. Do not implement more than one vertical behavior packet at a time.
  1. Add the failing test first. Record the initial failing output in the task summary.
  1. Use deterministic clocks, IDs, and fixture data. Production code must not call time.Now() or generate random IDs inside critical domain logic without an injected interface.
  1. Do not use Ref.1 + Ref.2 as a unique key.
  1. Do not depend on returned-PDF page order or an assumed descending room sort.
  1. Do not use an in-memory database to prove room locking, uniqueness, transaction, or idempotency behavior. Those tests use real PostgreSQL.
  1. Do not mutate golden fixture files during tests.
  1. Do not use real resident, contract, bank, SCB, or university data.
  1. Do not expose raw SeaweedFS/S3 URLs.
  1. Do not overwrite superseded payment, contract, export, or university-handoff history.
  1. Do not weaken permission or audit checks merely to make a test pass.
  1. Do not skip failing P0 tests. A skip requires a linked blocker and human approval.
  1. Do not refactor unrelated modules in the same task packet.
  1. End every task with targeted tests, module tests, and the required broader gate from this page.

Required test manifest

Create tests/manifest.yaml as the machine-readable source of test traceability.

- id: HOLD-001
  title: atomic exact-room hold
  priority: P0
  layer: integration
  requirement: exact-room reservation
  sprint: 5
  fixture: shared-room-base
  command: make test-id TEST=HOLD-001
  owner: backend
  status: Ready
  provisional: false

Rules:

  • IDs are never reused.
  • Retired tests remain in the manifest with a reason.
  • A provisional policy test has provisional: true and references the open decision.
  • Every P0/P1 requirement has at least one manifest entry.
  • The manifest is validated by make test-manifest.

Recommended test stack

Go backend

  • Standard testing package with table-driven tests.
  • testify/require or an equivalent small assertion helper.
  • go-cmp for structured comparisons where useful.
  • httptest for HTTP handlers.
  • Real PostgreSQL through a dedicated Docker test service or testcontainers-go for integration/concurrency tests.
  • Migration tests run against an empty database and a database upgraded from the previous schema.
  • Fakes only for deterministic boundaries such as clock, ID generator, email/notification, object storage adapter, PDF text extractor, and external file reader.

Nuxt frontend

  • Vitest for composables, stores, validators and utilities.
  • Vue Test Utils for components.
  • Mock Service Worker or a typed API stub for frontend integration tests.
  • Playwright for applicant and staff end-to-end journeys.
  • Accessibility assertions for labels, keyboard navigation, countdown announcements and status meaning.

Document contracts

  • Golden fixture files for XLSX, returned PDFs, result reports, contracts and university exports.
  • Structural XLSX comparison rather than raw binary comparison when workbook metadata can vary.
  • Original PDF checksum plus page-level extracted-text snapshots.
  • OCR fixtures only for an explicitly image-only PDF fallback.

Required end-to-end journeys

Use Playwright against the full Docker test stack with seeded fictional data. Each journey verifies visible UX, API/domain state, database state, file relationships and audit events.

E2E-001 — Shared normal room happy path

Applicant A and B complete profiles
→ A invites B
→ B accepts
→ A selects exact normal room
→ B confirms within 15 minutes
→ separate ROOM obligations created
→ finance exports SLIPS
→ returned PDF imported and matched
→ both residents pay through result-report fixture
→ staff confirms reservation
→ two contracts generated
→ both signed scans received
→ separate key handover recorded

Pass conditions:

  • one room assignment and two resident members;
  • no HL obligation;
  • one shared deadline;
  • correct private payment pages;
  • exact room remains confirmed throughout contract/handover completion.

E2E-002 — Shared HL room

Same journey as E2E-001, but each resident has ROOM and HL. Reservation cannot confirm when only ROOM is paid.

E2E-003 — Whole-room rental

One applicant selects whole-room occupancy, receives full-room obligation(s), permanently blocks second slot, completes one contract and one handover.

E2E-004 — Roommate confirmation timeout

Leader reserves room, roommate does not confirm, deterministic clock advances 15 minutes, room releases and another group can reserve it.

E2E-005 — Payment-hold timeout with one paid roommate

One resident pays, second remains unpaid, deterministic clock advances to 72-hour expiry, group follows provisional release/manual-refund path without losing paid transaction history.

E2E-006 — Manual staff reservation and payment

Authorized staff creates exact-room reservation and records manual payment with reference/note. No resident confirmation is required; permission and audit checks are verified.

E2E-007 — SCB PDF ambiguity and manual rematch

Returned PDF contains repeated references and one ambiguous page. System refuses unsafe auto-match; finance reviewer rematches with reason; resident receives correct page.

E2E-008 — Payment exception

Result report contains underpayment or post-expiry payment. Room is not confirmed automatically; finance resolves or records next action with audit history.

E2E-009 — Annual renewal with one roommate replaced

Previous data is prefilled, one resident renews, replacement joins, old obligations/contracts are superseded, new annual records are created, and room history stays intact.

E2E-010 — Shared to whole-room conversion after payment

One roommate has paid. Conversion creates new full-room obligations, preserves old paid/superseded records and requires correct financial review before final confirmation.

E2E-011 — University correction after handoff

Original confirmed resident export is marked submitted; roommate/amount changes later create a correction batch linked to original without overwrite.

E2E-012 — Cross-scope security journey

A staff user from the wrong dorm scope attempts room, payment PDF, result, contract and handover actions. Every action is denied and no sensitive data is returned.

Concurrency test harness

Critical concurrency tests must use real PostgreSQL and synchronization barriers, not timing sleeps.

Required harness pattern:

1. Seed exact known state.
2. Open independent database connections/transactions.
3. Block workers at a barrier immediately before critical statement.
4. Release all workers together.
5. Collect results.
6. Assert exact winner count, final rows, events and idempotency records.
7. Repeat enough times to detect race regressions without relying on randomness.

Required concurrency cases:

  • HOLD-001 — two groups acquire one room.
  • HOLD-008 — expiry versus final confirmation.
  • ROOM-002 — duplicate room import.
  • GROUP-002 — two invitations/groups for one resident.
  • RESULT-004 — one transaction applied to two obligations.
  • RESULT-013 — result import versus manual payment.
  • RESV-005 — repeated final confirmation.
  • renewal move from old room to new room while another applicant reserves the target.
  • correction export created twice for one change event.

Coverage and quality gates

Line coverage is secondary to state/contract coverage, but use it as a regression signal.

Minimum gates:

  • 100% of documented P0 state transitions have at least one positive and one negative test.
  • 100% of permissions in Page 04 have allow and deny tests.
  • 100% of SCB required columns have contract tests.
  • 100% of payment exception categories in fixture page have tests.
  • Critical domain/service packages target at least 90% statement coverage.
  • Overall backend target at least 80% statement coverage.
  • Frontend stores/composables/validators target at least 80%.
  • No flaky P0 test is accepted; fix determinism rather than adding retries.
  • No skipped P0/P1 test without a blocker record.
  • Every bug discovered after merge receives a regression test ID before the fix is accepted.

Test environment isolation

  • Unit tests run without network/database.
  • Integration tests use a dedicated PostgreSQL database or isolated schema per suite.
  • Parallel tests must not share mutable fixture rows unless concurrency is the behavior under test.
  • E2E runs use a uniquely named environment and seeded clock/config.
  • Object storage keys include test-run ID.
  • Background jobs are disabled or manually triggered unless the test specifically covers scheduling/recovery.
  • Test cleanup failure is a test failure, not ignored output.

Fixture and golden-file governance

  1. Fixture files are versioned and fictional.
  1. Every external sample has a README describing provenance and whether it is synthetic, anonymized or stakeholder-approved.

  1. Store fixture checksums in the test manifest where compatibility is critical.
  1. Never overwrite the only previous golden when changing a contract; retain versioned fixture directories.
  1. SCB/university unknowns use clearly named provisional fixtures.

Bug regression protocol

For every defect:

  1. Assign or extend a test ID.
  1. Reproduce with the smallest deterministic fixture.
  1. Commit/add the failing regression test first.
  1. Fix the narrowest production layer.
  1. Run targeted, module and relevant E2E/security gates.
  1. Add root cause and prevention note.
  1. Never close a money, room-lock or privacy defect without a regression test.
